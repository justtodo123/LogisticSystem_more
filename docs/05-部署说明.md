# 05 — 部署说明

> 最后更新：2026-09-01 | 面向：运维/部署人员

## Docker 部署（推荐）

> 验证级别（2026-08-19）：仓库已有 `docker-compose.yml`、`Dockerfile.*` 与 CD 镜像构建。本机未安装 Docker，**不得**将“文件存在”写成 Compose 启动或业务 E2E 已验收。跟踪：[plan 02](../My_doc/plan_todo/02-docker-seed-e2e.md)。

### 一键启动

```bash
git clone https://github.com/justtodo123/LogisticSystem_more.git
cd LogisticSystem_more
docker compose up -d
```

Compose 先运行一次性 `migrate` 服务执行 `python scripts/release_migrate.py`；它只为 fresh SQLite 建库，或验证已处于当前 head 且 schema parity 通过的现有库。旧版、漂移或未知 SQLite 会 fail closed，不做原地 DDL；仅在门禁成功后启动 backend。应用镜像的 Uvicorn CMD 本身不执行 DDL，避免多 worker 竞态。首次初始化演示数据需在 backend 就绪后单独运行：

```bash
docker exec -it logistics-backend python scripts/init_demo_data.py
```

旧 SQLite 不得直接挂载后试错。先备份并在后端目录使用 `python scripts/migrate_sqlite.py classify|upgrade-copy|adopt-copy`，验证副本后再切换数据卷。

启动三个长期服务（`migrate` 成功后退出）：

| 服务 | 容器名 | 端口 | 说明 |
|------|--------|------|------|
| backend | `logistics-backend` | `8000` | FastAPI + uvicorn，SQLite 数据卷持久化 |
| redis | `logistics-redis` | `6379` | 缓存 + 幂等存储（AOF 持久化） |
| frontend | `logistics-frontend` | `8080` | Nginx 托管，`/api` 反向代理到 backend |

访问：
- 前端：[http://localhost:8080](http://localhost:8080)
- 后端 API 文档：[http://localhost:8000/docs](http://localhost:8000/docs)
- 健康检查：[http://localhost:8000/api/health](http://localhost:8000/api/health)

### 生产密钥注入

不要修改 `docker-compose.yml`。创建 `docker-compose.override.yml`（已 gitignore）：

```yaml
services:
  backend:
    environment:
      JWT_SECRET: "<生产随机密钥>"
      DEEPSEEK_API_KEY: "<你的 DeepSeek API Key>"
      MAP_API_KEY: "<高德地图 Key>"
```

### P1 PostgreSQL + Redis 拓扑

默认 `docker compose up` 仍是 SQLite + 单 worker，不能当作 R2-05 验收。

P1 栈使用独立文件，仅在 Linux / 云主机 / 已有 Docker Engine 的环境执行：

```bash
docker compose -f docker-compose.p1.yml -p logistics-r2 up -d --build
```

包含 PostgreSQL 16、Redis 7、一次性 `release_migrate`、uvicorn `--workers 2` 与独立 outbox worker。本机 Windows 宿主未安装 Docker，因此该命令在本仓库当前开发机上**未执行**。

### 生产数据库切换

默认使用 SQLite。切换 PostgreSQL：

```yaml
services:
  backend:
    environment:
      DATABASE_URL: "postgresql://user:pass@postgres:5432/logistics"
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: logistics
    volumes:
      - pgdata:/var/lib/postgresql/data
```

## 镜像构建

### 手动构建

```bash
# 后端
docker build -f Dockerfile.backend -t logistics-backend:latest .

# 前端
docker build -f Dockerfile.frontend -t logistics-frontend:latest .
```

### Dockerfile 要点

**后端** (`Dockerfile.backend`)：
- `FROM python:3.13-slim`
- 先 COPY `requirements.txt` 安装依赖（利用 Docker 层缓存）
- 再 COPY 全量源码
- 创建 `/app/data`（SQLite 卷挂载点）
- `EXPOSE 8000`
- HEALTHCHECK：`curl -f http://localhost:8000/api/health`
- CMD：`uvicorn main:app --host 0.0.0.0 --port 8000`（不执行迁移）
- 发布/预启动阶段必须先使用同一镜像和同一 `DATABASE_URL` 单独执行 `python -m alembic -c alembic.ini upgrade head`

**前端** (`Dockerfile.frontend`)：
- 多阶段构建：`node:22-alpine` 构建 → `nginx:1.27-alpine` 托管
- Nginx 配置 `/api/` → `backend:8000`（Docker 网络内服务名）
- SPA 回退：`try_files $uri /index.html`
- `EXPOSE 80`

## CI/CD

### CI（Push/PR → main）

`.github/workflows/ci.yml` 四个 job：

| Job | 运行环境 | 步骤 |
|-----|---------|------|
| `migration-check` | ubuntu + Python 3.13 | 唯一 head → fresh upgrade → `alembic check` → legacy/unknown/index 专项测试 |
| `backend-test` | ubuntu + Python 3.13 | pip install → `pytest -q` |
| `p1-postgres-redis` | ubuntu + Python 3.13 + postgres:16-alpine + redis:7-alpine | `release_migrate` → PostgreSQL CAS/幂等/号段/Saga/outbox 协议复跑 → 两个可单独寻址 Uvicorn 进程 + 独立 outbox worker → HTTP smoke 与跨进程 JWT/幂等 |
| `frontend-check` | ubuntu + Node 22 | npm ci → `npm run build`（vue-tsc + vite build） |

特性：pip/npm 依赖缓存 + concurrency 取消冗余运行。`p1-postgres-redis` 现覆盖协议复跑与双进程 HTTP；仍不等于故障注入、恢复或备份验收。

### CD（Push → main，CI 通过后）

`.github/workflows/cd.yml`：
- 构建 `logistics-backend:latest` + `:sha` 双 tag
- 构建 `logistics-frontend:latest` + `:sha` 双 tag
- 推送到 GitHub Container Registry（GHCR）
- 镜像名强制小写处理

当前 CD 只发布镜像，不连接部署数据库。实际部署平台必须另设单实例 release migration：先备份/分类旧库，再以待发布后端镜像运行 `python -m alembic -c alembic.ini upgrade head`；成功后才能滚动应用实例。失败时停止发布，SQLite 从备份或未修改源文件恢复，不使用 `stamp head` 掩盖失败。

## 生产环境变量

部署到生产时需要覆盖以下变量（完整列表见[环境配置说明](环境配置说明.md)）：

| 变量 | 说明 |
|------|------|
| `JWT_SECRET` | **必须更换**，至少 32 位随机字符串 |
| `DATABASE_URL` | PostgreSQL 连接串（SQLite 仅用于开发） |
| `CORS_ORIGINS` | 前端域名（如 `https://logistics.example.com`） |
| `DEEPSEEK_API_KEY` | DeepSeek API Key（不填则 AI 功能全部返回降级） |
| `MAP_API_KEY` | 高德/百度地图 Key（不填则地图降级折线） |
| `REDIS_ENABLED` | 生产应为 `true` |
| `ERP_API_KEY` | ERP 对接 API Key |
| `ENV` | 改为 `prod` |

## 数据持久化

`docker-compose.yml` 定义两个命名卷：
- `logistics-data` → `/app/data`（SQLite 数据库文件，`migrate` 与 backend 共用）
- `logistics-redis` → `/data`（Redis AOF 文件）

SQLite 发布前应复制数据库文件并记录哈希；受控工具只升级副本。迁移或 parity 失败时保留原文件并停止启动，修复后前向重试或恢复备份。不要把 Alembic downgrade 当作 SQLite 的通用恢复机制。
