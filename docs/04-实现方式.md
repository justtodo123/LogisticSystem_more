# 04 — 实现方式

> 最后更新：2026-09-04 | 面向：理解核心机制设计

## 1. 状态机 — 单权威入口

订单状态流转的唯一出口是 `services/state_machine.py` 中的 `ORDER_TRANSITIONS` 字典。所有状态变更必须经过 `OrderService.update_state_after_f005()`，禁止各模块直接修改 `order.status`。

```python
# 状态变迁定义（state_machine.py，与 core.order_status 对齐）
ORDER_TRANSITIONS = {
    "unassigned": ["assigned", "closed"],
    "assigned":    ["in_transit", "closed"],
    "in_transit":  ["signed", "exception"],
    "signed":      ["exception"],            # 签收后仍可发现异常
    "exception":   ["assigned", "in_transit", "closed"],
    "closed":      [],                       # 唯一硬终态
}
```

这种设计的优势：
- 状态合法性在单一位置校验，不会出现跨模块不一致
- 新增状态只需在一处添加，服务层自动继承

2026-08-19 起前后端/Mock/种子共用上述六态；历史四态仅允许一次性回填，未知值原样暴露。货物 `delivered` 为终态，重规划不再回退，见 [plan 01](../My_doc/post_plan/第一轮优化计划/01-delivered-goods-replan-integrity.md)。

## 2. 调度管线 — 策略模式 + 多目标评分

```
Pending 订单
    │
    ▼
GlobalSchedule (L0→L1→L2 全链路)
    │  策略：GreedyGlobalScheduleStrategy
    │  L0: 订单→就近仓储中心
    │  L1: 仓储→分拣中心（容量 + 时窗约束）
    │  L2: 分拣中心→末端网点
    │
    ▼
NodeDispatch (车辆分配)
    │  策略：GreedyNodeDispatchStrategy
    │  候选生成 Top-K
    │
    ▼
Multi-Objective Scoring (scoring.py)
    │  5 目标：距离/成本/时效/负载率/均衡度
    │  归一化 → 加权 → 排序 → Top-1 + 备选
    │
    ▼
Route Planning (route_planning.py)
    │  当前按既有顺序生成路线；`_two_opt()` 仍是 stub
    │  距离计算：真实路网 → 直线×系数(1.3) → Haversine 三档降级
    │
    ▼
[确认] Packaging (packaging.py)
    同一路线订单 → 包裹 → active 调度
```

调度引擎通过策略模式实现可插拔：

```
SchedulingStrategy (ABC)          ← base.py
├── GreedyGlobalScheduleStrategy ← algorithms/global_schedule.py
├── GreedyNodeDispatchStrategy   ← algorithms/node_dispatch.py
└── DummyStrategy                ← 调试/协议验证

StrategyFactory (factory.py)
  全局调度与节点调度当前注册 `greedy` / `dummy`
  未知 engine 自动回退 `greedy`
  DeepSeek 只做解析、解释和建议，不是已注册调度 engine
  route_planning.py 中 `_two_opt()` 仍为 stub，不应宣称已完成 2-opt 优化
```

## 3. AI 闭环 — 校验层 + 确认闸门

AI 自然语言解析不是直接"AI 调度"，而是**参数建议 + 人工确认**的闭环：

```
用户输入 "优先时效，城市 A 到 B"
    │
    ▼
DeepSeek API 解析 → JSON 参数
    │
    ▼
Pydantic Schema 校验 (schemas/ai_output.py)
    │  失败 → 错误反馈 → AI 重试（最多 3 次）
    │  耗尽 → 降级为默认参数
    │
    ▼
业务规则闸门 (core/ai_guard.py)
    │  权重和 ≈ 1.0 / 类型白名单 / 级别分类
    │
    ▼
创建 AiSuggestion (pending)
    │  级别: info(仅展示) | suggestion | action
    │
    ▼
人工确认闸门 (api/ai_confirmation.py)
    │  POST confirm → 调用 ScheduleService.confirm_schedule
    │     F021 打包 → draft→active → 实际调度生效
    │  POST reject → 标记 rejected，不触发调度
```

## 4. 缓存降级 — Redis → 内存自动切换

`utils/cache.py` 提供 `@cached` 装饰器：

```
装饰器 @cached(ttl=300, prefix="nodes")
    │
    ├─ REDIS_ENABLED=true
    │    → Redis 存储，key=prefix:args_hash
    │    → 写入操作自动失效 (delete_prefix)
    │
    └─ REDIS_ENABLED=false
         → 进程内存 dict 存储
         → 重启后缓存丢失（可接受，仅预热影响）
```

所有写操作（创建/更新/删除）主动失效相关缓存前缀，保证缓存一致性。

## 5. 距离计算 — 三档降级

`services/map_service.py` 的 `get_route_distance()`：

| 优先级 | 来源 | 精度 | 触发条件 |
|--------|------|------|----------|
| 1 | 高德/百度路网 API | 真实道路距离 + ETA | `MAP_API_KEY` 有效且 API 正常 |
| 2 | 直线距离 × 系数(1.3) | 估算道路距离 | `MAP_ROAD_APPROX=true` 或 API 调用失败 |
| 3 | Haversine 公式 | 球面直线距离 | 无 API Key、系数模式也失败 |

每层失败自动下降，结果缓存 1 小时，`route_planning` 接入时标识 `road_name` 来源。

## 6. 异常重规划 — 三策略 + 差异报告

`services/replan_service.py` 提供三种策略：

| 策略 | 含义 | 适用场景 |
|------|------|----------|
| `partial` | 仅重新调度受影响订单，保留未受影响部分 | 单件/少量异常 |
| `full` | 所有未完成订单全部重调度 | 大面积异常（车辆故障） |
| `hybrid` | partial 优先，如果无解则回退到 full | 不确定影响范围 |

每次重规划生成差异报告（`diff_service.py`），对比新旧方案的 distance/time/goods 变化，响应含 `diff_summary`。

## 7. 数据库权威幂等 — lease + claim token + 原始响应重放

`middleware/idempotency.py` 对带 `Idempotency-Key` 的写请求协调数据库记录，正确性真相源是 `idempotency_records`，不是 Redis 或进程内字典：

```
PROCESSING ──业务成功──> SUCCEEDED
     │                         │
     ├─失败/异常──────> FAILED  └─相同 key：重放原始响应
     └─lease 到期─────> EXPIRED → 新 owner 可安全接管
```

- claim 保存 payload fingerprint；相同 key 的不同 payload 返回 `40903`，处理中返回 `40902`。
- claim/finalize 使用 claim token；lease 回收后旧 owner 不能覆盖新 owner。
- 成功记录保存原始 HTTP status、response bytes、media type 和安全响应头，replay 不重复执行业务逻辑；Redis 只缓存已提交成功的 replay，故障时回到数据库。
- 业务事务与 `mark_succeeded` 之间仍有崩溃窗口，因此对外只能描述为持久化幂等/重放，不能声称 exactly-once。

## 8. 消息通知 — transactional outbox

`services/notification/` 提供 Console、SMTP、企业微信渠道。业务状态和 outbox event 在同一数据库事务提交，由独立 worker 以短生命周期 Session 投递：

- worker 使用 lease/claim token 防止旧 worker 迟到写入，失败事件按 retry/backoff 重试，超过上限进入 dead-letter；补偿失败进入 `manual_required`。
- API 请求事务内不直接发送 SMTP/Webhook；外部发送端没有幂等能力时，至少一次尝试可能产生重复通知。
- Redis 仅用于普通缓存和可选登录限流，不承担 outbox 或幂等正确性。

```
notification/
├── base.py           # 渠道抽象接口
├── console.py        # 控制台打印（dev 默认）
├── email.py          # SMTP 邮件
├── wechat_work.py     # 企业微信机器人 Webhook
├── dispatcher.py     # 渠道分发器（读 notification_configs 表）
└── templates/        # 消息模板渲染
```

运行时可通过 `PUT /api/notifications/config` 切换渠道；业务主事务只写 outbox，通知投递结果由 worker 的重试/dead-letter 状态追踪。

## 9. CAS、原子编号与可恢复 Replan

- **CAS 状态转换**：关键状态更新采用 `UPDATE ... WHERE id=? AND state=?`，以 `rowcount` 判定唯一赢家；只有 CAS 成功者执行包装、关联订单/货物和事件等副作用，失败竞争者稳定映射为 `40901`。
- **原子业务编号**：`code_ranges` 通过数据库条件更新分配号段，替代 `max+1`、`count+1` 和进程内序号；SQLite 证据只说明协议正确性，PostgreSQL 16 的 8-worker/100,000 claims 是独立编号专项，不代表完整订单写路径或生产容量。
- **Replan Saga**：task/step 状态持久化，lease 允许超时接管，claim token 提供 fencing；业务状态和 outbox 同事务提交，补偿失败进入 `manual_required`，便于人工处理而不是静默丢失。
