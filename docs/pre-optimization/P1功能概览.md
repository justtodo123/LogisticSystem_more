### P1-03 · 全局调度：条件筛选 + 预览确认

**现状**：全局调度主要依据 **pending 状态订单** 自动生成；生成即落库并改变订单/包裹状态。

**目标**：

1. 用户 **自行选择条件** 参与调度（不限于 pending），例如：多选订单、按目的地/时间/状态筛选。
2. **预览模式**：生成方案但不立即改库；用户 **确认选用** 后才更新订单及包裹信息。

**执行要点**：

| 端 | 内容 |
| --- | --- |
| 后端 | `POST /api/schedule/global` 增加 `order_codes[]` / 筛选参数；增加 `preview=true` 或独立 preview 接口；确认接口 `POST .../confirm` 落库 |
| 前端 | 订单多选 + 筛选 UI；「生成预览」「确认采用」两步流；预览态明确标识 |
| 数据 | 可选：`draft_schedules` 或内存/临时表存预览方案（简化版可用 session 级不落库预览） |

**与老师意见关联**：多选订单、按条件指定调度（老师意见 2）。

### P1-08 · 节点到货确认（单包裹正常 / 异常）

**原则**：**不修改** MVP 的 `ExceptionList` + F013 异常重规划；**新增**独立页面「节点到货确认」。

**要解决的问题**：L0→L1 到站后，MVP 会把该节点所有 L1→L2 预生成包裹（如 F）一律 `pending_pack → packed`，即使对应货物（如 g_2）因上游包裹 D 异常并未到站。

**业务背景（F007 + F021）**：

| 层级 | 节点 | 包裹 | 说明 |
| --- | --- | --- | --- |
| L0→L1 | n_1 | C(g_1)、D(g_2) | F021 后 `packed` |
| L1→L2 | n_2 | E(g_1)、F(g_2) | 初始 `pending_pack`，**仅当 g 实际到达 n_2 才激活** |

**演示步骤摘要**（完整见 [P1开发计划 §1.4.3](./P1开发计划.md#143-演示步骤与状态预期)）：

1. F007+F021 → C/D packed，E/F pending_pack，订单 delivering  
2. F005 L0→L1 → C/D in_transit  
3. **n_2 到货确认**：C 正常、D 异常 → E packed，**F exception**（非 packed），g_2 exception，O_2 exception  
4. F005 L1→L2 → 仅 E 可 in_transit，**F 保持 exception**  
5. 模拟送达 → g_1 delivered，**F/g_2 仍为 exception**

**级联规则**：

- **正常**：到站包裹 `delivered`；货物按是否到目的地 → `packed`/`delivered`；**仅对该货物**激活下游 `pending_pack → packed`  
- **异常**：到站包裹 `exception`；货物 `exception`；**含该货物的下游预生成包裹** → `exception`；订单 → `exception`  
- **F005**：`exception` 包裹不可调度  
- **模拟送达**：不得将 `exception` 包裹/货物改为 `delivered`

**执行要点**：

| 端 | 内容 |
| --- | --- |
| 后端 | 新 API `arrival-packages` / `confirm-arrival`；改造 `simulation_service` 批量激活逻辑；F005 过滤 exception |
| 前端 | 新页：选方案 + 节点 → 到站包裹列表 → 每条正常/异常 → 提交 |
| 契约 | [api-contract-p1-3.md](./api-contract/api-contract-p1-3.md) |
