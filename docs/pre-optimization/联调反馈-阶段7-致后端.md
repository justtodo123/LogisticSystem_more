### 后端逻辑理解摘要（对照契约 §9）

| # | 问题 | 结论（代码 + 实测） |
|---|------|---------------------|
| 1 | 创建 **node** 异常后，哪些实体被标 `exception`？ | [`exception_service.create_exception_event`](../src/backend/services/exception_service.py)：按 `related_schedule_code` 找 `GlobalSchedule`，将该方案下 **`delivering` 订单 → `exception`**，其货物 `packed/in_transit` → `exception`；**`Package.schedule_id` 匹配** 且状态为 `packed/in_transit/pending_pack` → `exception`。与契约 §9.4「按方案关联」一致；**全方案包裹批量标记**，非仅目标节点 L1001。 |
| 2 | **redispatch** 成功后包裹状态？ | [`schedule_service` + `packaging`](../src/backend/algorithms/packaging.py)：`is_replan=True` 时仅将 **`exception` 货物** 重新打包为 **新** `packed` 包裹；**旧包裹记录仍保持 `exception`**。实测 redispatch 后：`exception` 76、`packed` 26。与「异常货物被重调度」一致，但 UI 筛选 `exception` 仍会看到大量历史包裹（演示时注意）。 |
| 3 | **`resolve`** 是否只改事件状态？ | **是**。`resolve_exception` 仅写 `exception_events.status=resolved` 与 `resolved_at`；**不恢复**订单/包裹/货物状态。 |

### P1 建议（非阻塞）

| 项 | 说明 |
|----|------|
| 清库与 Alembic | 全新库请 `init_db()` + seed + `alembic stamp head`；直接 `upgrade head` 会因 `exception_events` 表不存在而失败 |
| redispatch 返回 `batch_code` | 实测 `replan` 响应 `batch_code: null`，`GET /schedule/batches?schedule_code={v2}` 为 0；`replan_service` 内联调用了 `create_node_dispatch`，可能因无可调度 `exception` 包裹而失败但不影响主结果——答辩若需展示批次，建议先确认 v2 下 `node-dispatch` 或查 `event.replan_batch_code` |
| 包裹 `exception` 残留 | 创建异常时**整方案**包裹标 `exception`；redispatch 只对新打包货物生效，旧包裹行仍为 `exception`——与契约「重规划处理 exception 货物」一致，但与用户直觉「重规划后异常应清零」有落差；可在 PRD/答辩话术或后续迭代中说明 |
| `deliver {}`（`demo_mode=true` 回归） | `code=40001`，`没有找到可送达的包裹`（demo 模式批次直接 `completed`，无 `in_transit`）；与阶段 6 一致，真实演示用 `demo_mode=false` + 分步送达 |
| 自测脚本 reset | `phase7_integration_test.py` 中段 `reset_db()` 在 uvicorn 占用 SQLite 时会失败；**先停后端**再跑全量脚本，或分两段：reroute / redispatch 各用独立清库 |
| `main` 分支勿联调 F013 | `main` 上异常 API 仍为 501 + 旧 Schema，会出现 HTTP 422 |
