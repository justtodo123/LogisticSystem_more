## 1. 目标

- 联调在**本地临时分支**完成，不污染 `frontend/phase-N` / `backend/phase-N` 的提交历史
- 每阶段有统一的**环境、验收清单、反馈格式**
- 联调通过后再按 Git 规范提 PR 合 `main`

---

## 2. 何时开始联调

满足以下条件再开联调（避免半成品浪费时间）：

| 角色 | 前置条件 |
| --- | --- |
| 后端 | 本阶段 API 在 Swagger/Postman 自测通过；`origin/backend/phase-N` 已 push |
| 前端 | 本阶段页面可跑通（Mock 或真实 API）；`origin/frontend/phase-N` 已 push |
| 两人 | 对照 `docs/api-contract/api-contract-phaseN.md` 确认字段一致 |

阶段 0、1、2… 凡 MVP 计划写明「必须与对方联调通过」的，均按本文执行。

## 3. 临时联调分支 `integration/phase-N`（核心流程）

> 原则：**阶段内各自分支开发，联调在 `integration/phase-N` 本地合并验证，通过后再 PR 合 `main`。**

### 3.1 创建集成分支

**方式 A（推荐，阶段 2+）**：从前端分支拉出，合并远端后端

```bash
cd e:\LogisticsSystem
git fetch origin

# 将 N 换成当前阶段号
git checkout frontend/phase-N
git pull origin frontend/phase-N

# 删除旧的本地集成分支（若存在）
git branch -D integration/phase-N

git checkout -b integration/phase-N
git merge origin/backend/phase-N --no-edit
```

**方式 B（阶段 0 等从零叠代场景）**：从 `main` 拉出，先后端再前端

```bash
cd e:\LogisticsSystem
git fetch origin
git checkout main
git pull origin main
git checkout -b integration/phase-N

git merge origin/backend/phase-N --no-edit
git merge origin/frontend/phase-N --no-edit
```

### 3.2 集成分支约束

| 规则 | 说明 |
| --- | --- |
| **默认不 push** | `integration/phase-N` 仅本地使用，避免远程脏分支 |
| **不在此分支长期开发** | 仅用于验证；修复应回到各自 `frontend/` / `backend/` 分支 |
| **可多轮联调** | 对方修完后 `git fetch` + 重新 merge 或按 §3.1 重建集成分支 |
| **禁止 force push** | 不对 `main` 或对方分支做 force push |

### 3.3 合并冲突

```bash
# 在 integration/phase-N 上解决冲突后
git add .
git commit -m "merge: 阶段N联调合并 backend/phase-N"
# 不要 push integration/phase-N（除非两人约定）
```

拿不准时语音/屏幕共享一起改；**以契约文档 + 已验收的 main 逻辑为准**。

## 4. 联调环境

### 4.1 后端

```powershell
cd src\backend
.\.venv\Scripts\Activate.ps1
$env:PYTHONUTF8=1
$env:PYTHONPATH="."

# 阶段 2+ 需要演示数据时
Remove-Item -Force data\logistics.db -ErrorAction SilentlyContinue
python -c "from config.database import engine, Base; from models import *; Base.metadata.create_all(bind=engine)"

```

### 4.2 前端

确认 `src/frontend/.env.local`：

```env

VITE_USE_MOCK_AUTH=false
VITE_USE_MOCK_BASIC_DATA=false   # 阶段 2+ 联调必须 false
```

```bash
cd src/frontend
npm run dev
```

访问：http://localhost:5173  
账号：`dispatcher / 123456`，`manager / 123456`

| --- | --- |
| `GET http://localhost:8000/api/health` | 200 |
| 前端登录 | 成功拿到 token |

## 5. 验收清单（按阶段勾选）

- [ ] 分页格式 `{ items, total, page, page_size }` 正常

### 5.2 阶段 0：工程初始化

- [ ] 前端 `/api/health` 代理成功

- [ ] 登录 / 登出 / 刷新保持登录

## 6. 问题反馈

### 6.1 反馈文档

阻塞问题写入：`docs/联调反馈-阶段N-致后端.md`（或 `-致前端.md`）

**模板结构**：

1. **消息正文**（可直接复制发给对方）
2. **环境**（分支、commit、Mock 开关）
3. **已通过项**
4. **需修复项**（P0/P1/P2 + 复现步骤）
5. **附录**（请求示例、前端临时兼容说明）

阶段 2 示例：[联调反馈-阶段2-致后端.md](./联调反馈-阶段2-致后端.md)

### 6.2 优先级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 阻塞联调（500、RBAC 失效、核心流程不通） | 对方修完再开一轮 |
| P1 | 字段缺失、校验不符契约 | 本轮可记债，下轮必须修 |
| P2 | 体验/筛选增强 | 可进 PR 后迭代 |

### 6.3 多轮联调

```bash
git fetch origin
git checkout integration/phase-N
git merge origin/backend/phase-N --no-edit   # 或按 §3.1 重建集成分支
# 重新建库、启动、跑验收清单
```

每轮结束在反馈文档末尾追加「第 X 轮联调结论」。

## 7. 联调通过后的动作

1. **各自分支**：把联调中发现的小修复 commit 到 `frontend/phase-N` 或 `backend/phase-N`（不要留在 `integration/phase-N`）
2. **提 PR**（顺序见 [Git协作规范 §5.2](./Git协作规范.md)）：
   - 先后端：`main` ← `backend/phase-N`
   - 再前端：`main` ← `frontend/phase-N`（merge 最新 main 后再联调一次）
3. **两人** `git checkout main && git pull origin main`
4. **开下一阶段**：从最新 `main` 拉 `frontend/phase-(N+1)` / `backend/phase-(N+1)`
5. **删除本地** `integration/phase-N`（可选）

## 8. 禁止事项

| 禁止 | 原因 |
| --- | --- |
| 在 `main` 上直接联调 | 污染稳定分支 |
| 联调未通过就 PR | 浪费 Review 时间 |
| 提交 `.env`、`*.db` | 安全与仓库卫生 |
| 长期把 `integration/phase-N` push 到远程 | 易与对方分支混淆（除非两人约定） |
| 联调时开着 Mock 却声称已联调 | 假通过 |
