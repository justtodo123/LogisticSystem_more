## 一、产品概述与版本范围

### 1.1 产品定位

本项目为**教学实训项目**（华中科技大学软件学院，2026年6月，4周周期），旨在构建一个智能物流调度平台演示系统。平台核心是通过**DeepSeek大模型**赋能物流调度决策，实现"订单生成→全局调度→节点间调度→路径规划→AI解释与建议"的完整业务闭环。

项目定位为**可演示的教学版本**，不追求生产级性能，但要求业务流程完整、智能化能力可展示、技术架构可扩展。

**核心能力提升**：

- **传统算法**：基于规则评分+启发式算法（P0，本版本实现）
- **AI模型**：基于深度学习/强化学习的智能调度模型（P1，后续迭代）
- **DeepSeek智能编排**：解析用户自然语言输入，生成算法参数，调用系统算法生成调度方案

### 1.2 背景假设与物流模型

#### 1.2.1 背景假设

本项目为智能物流调度平台演示系统，基于以下核心假设构建：

1. **物流网络结构假设**：
   - 物流网络采用**三级层级结构**：存储中心（层级0）→ 1级分拣中心（层级1）→ 0级分拣中心（层级2）
   - 存储中心：货物存储起点，负责将货物发送至1级分拣中心
   - 1级分拣中心：物流中心，负责货物分拣和重新打包
   - 0级分拣中心：快递站/自提点，用户到此处自提货物
   - **注意**：一个层级中存在多个节点（如层级0有5个存储中心，层级1有2个1级分拣中心，层级2有50个0级分拣中心）

2. **运输单位假设**：
   - 运输的单位是**包裹**，不是订单
   - 一个订单包含多个货物，货物在存储中心打包成包裹
   - 包裹在1级分拣中心可能重新打包（将运往同一个0级分拣中心的货物打包在一起）

3. **调度单位假设**：
   - 调度分为两个层次：**全局调度**（F007）和**层级间调度**（F005）
   - 全局调度：确定每个货物的运输路径（存储中心→1级分拣中心→0级分拣中心）
   - 层级间调度：确定每个车辆在相邻层级间的运输任务（如层级0→层级1，或层级1→层级2）

4. **异常类型假设**：
   - **道路异常**：拥堵、车辆停留、道路封闭等
   - **包裹异常**：包裹损坏、包裹丢失等
   - **节点异常**：节点容量达到上限、节点存储时间达到上限、节点维修等
   - **异常处理原则**：道路异常和包裹异常触发**重新规划路径**（F006重新运行）；节点异常触发**重新调度**（F007/F005重新运行）

5. **数据假设**：
   - 所有地址字段（orders、packages、vehicles、nodes）都需要记录经纬度（冗余字段或关联查询）
   - 历史数据（historical_data表）用于AI模型训练（F007-1、F005-1）

#### 1.2.2 物流模型

本项目的物流模型基于以下核心概念构建：

1. **物流网络模型**：
   ```
   存储中心（层级0） → 1级分拣中心（层级1） → 0级分拣中心（层级2）
   ```
  - **节点类型**：
    - 存储中心（Storage Center）：`nodes`表（node_type='storage_center'），详情在`storage_centers`表
    - 1级分拣中心（Level-1 Sorting Center）：`nodes`表（node_type='sorting_center'），详情在`sorting_centers`表（level=1）
    - 0级分拣中心（Level-0 Sorting Center）：`nodes`表（node_type='sorting_center'），详情在`sorting_centers`表（level=0）
   - **节点关系**：相邻层级间的节点可以互相运输（如存储中心→1级分拣中心，1级分拣中心→0级分拣中心）

2. **运输流程模型**：
   ```
   订单（Order） → 货物（Goods） → 包裹（Package） → 运输（Transport） → 配送（Delivery）
   ```
   - **订单**：用户下单，包含多个货物和时效要求
   - **货物**：订单中的具体物品，有重量、体积、所属存储中心
   - **包裹**：运输单位，在存储中心或1级分拣中心打包生成
   - **运输**：包裹通过车辆从一个节点运输到另一个节点
   - **配送**：包裹到达0级分拣中心，用户自提（本系统默认为已完成）

3. **调度算法模型**：
   ```
   F007（全局调度） → F005（层级间调度） → F006（路径规划）
   ```
   - **F007（全局调度）**：输入订单列表，输出每个货物的运输路径（存储中心→1级分拣中心→0级分拣中心）
   - **F005（层级间调度）**：输入待调度包裹列表+车辆列表+下一层级节点列表，输出每辆车的任务列表（节点序列）
   - **F006（路径规划）**：输入某辆车的任务列表（节点序列），输出这辆车的全局道路路径（路段信息JSON）

4. **异常处处理模型**：
   ```
   异常检测 → 异常分类 → 重新调度（F007/F005）或重新规划路径（F006）
   ```
   - **异常检测**：用户手动标记或系统自动检测异常
   - **异常分类**：道路异常/包裹异常 → 重新规划路径；节点异常 → 重新调度
   - **重新调度**：F007（全局调度）和F005（层级间调度）重新运行，生成新的调度方案
   - **重新规划路径**：F006（路径规划）重新运行，生成新的路径方案

### 1.2.3 接口设计决策

在阶段2（基础数据管理）开发文档生成过程中，对以下接口设计决策进行了澄清和确认：

1. **订单创建接口设计决策**（对应F001）：
   - **决策**：创建订单时同时创建货物，`OrderCreate` Schema包含`goods`列表（`List[GoodsCreate]`）。
   - **理由**：简化前端操作，一次API调用完成订单和货物的创建，符合用户"录入订单信息"的自然流程。
   - **影响范围**：`POST /api/orders`接口的请求体格式、后端服务层实现。

2. **包裹重新打包接口设计决策**（对应F001-2）：
   - **决策**：重新打包接口（`POST /api/packages/{package_code}/repack`）的输入只包含`goods_codes`列表，不需要指定目标节点或重新计算重量体积。
   - **理由**：repack是在同一订单内重新分配货物到包裹，目标节点不变（仍是原订单的`destination_node`），重量体积由系统自动重新计算。
   - **影响范围**：`POST /api/packages/{package_code}/repack`接口的请求体格式、后端服务层实现。

3. **订单批量导入接口设计决策**（对应F001）：
   - **决策**：批量导入接口（`POST /api/orders/import`）的`skip_errors`参数默认值为`True`，即默认跳过错误行，返回部分成功结果。
   - **理由**：符合PRD中"部分成功（跳过错误行）"的描述，提高导入效率，用户体验更好。
   - **影响范围**：`POST /api/orders/import`接口的默认行为、前端调用方式。

4. **订单批量导入Excel/CSV格式决策**（对应F001）：
   - **决策**：批量导入接口（`POST /api/orders/import`）的Excel/CSV文件格式定义为7列：订单编号、配送节点编号、时效要求、货物名称、货物类型、重量(kg)、体积(m³)。
   - **理由**：明确文件格式便于前端开发和用户使用，避免格式歧义。
   - **影响范围**：`POST /api/orders/import`接口的文件上传格式、前端上传组件、用户操作手册。

### 1.3 产品目标

- 完成订单、货物、包裹、车辆、司机、存储中心、分拣中心基础信息管理，支持调度员查看和维护核心业务数据
- 实现基于规则评分+启发式算法的全局调度（F007，P0）、层级间调度（F005，P0）与路径规划（F006，P0）
- 实现路线可视化（静态图片）与模拟轨迹追踪，支持异常场景的重规划演示
- 接入DeepSeek作为智能调度助手，通过自然语言描述实现方案解释、审查和优化建议
- 形成可部署、可演示、可验收的前后端分离系统

#### 模块1：基础数据管理（P0）

##### F001 - 订单管理

**用户故事**：

- 作为调度员，我希望能够录入订单信息，以便进行全局调度
- 作为调度员，我希望能够批量导入订单数据，提高录入效率
- 作为调度员，我希望能够查看订单状态，了解配送进度

**功能描述**：

- 支持订单的增删改查
- 支持批量导入（Excel/CSV格式）
- 系统预置演示数据（初始化时自动生成）
- 订单状态跟踪：待分配/配送中/已完成/异常
  - 待分配：订单创建后，尚未被调度系统处理
  - 配送中：调度系统获取订单并生成调度策略后，订单进入配送中状态
  - 已完成：订单所有货物都到达最后一级节点（0级分拣中心），默认已完成（后续扩展需要顾客确认，本系统暂不实现）
  - 异常：订单在运输过程中发生异常
- **订单结构变更**：订单包含多个货物，订单的"收货地址"变为"0级分拣中心ID"

**验收标准**：

* [ ] 用户可以通过表单新增订单，必填字段：订单编号、0级分拣中心ID、时效要求
* [ ] 用户可以通过Excel模板批量导入订单，系统提示导入成功/失败数量
* [ ] 用户可以在订单列表查看所有订单，支持按状态筛选
* [ ] 用户可以编辑和删除待分配状态的订单；配送中/已完成/异常状态的订单不允许删除，只能标记为异常
* [ ] 订单编辑只能修改配送节点（destination_node_id）和时效要求（time_window），不能修改货物信息（货物信息需在货物管理界面修改）
* [ ] 系统初始化时自动生成不少于50条演示订单数据，每个订单包含2-7个货物

**数据字段**：

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| order_id | String | 唯一、非空、自动生成 | 订单编号（唯一） |
| destination_node_id | String | 非空 | 0级分拣中心ID（原收货地址） |
| time_window | String | 非空 | 时效要求（如"9:00-12:00"） |
| status | Enum | 非空 | 状态：待分配/配送中/已完成/异常 |
| created_at | DateTime | 自动生成 | 创建时间 |
| updated_at | DateTime | 自动更新 | 更新时间 |

##### F001-1 - 货物管理（新增）

**用户故事**：

- 作为调度员，我希望能够录入货物信息，以便进行全局调度
- 作为调度员，我希望能够查看货物状态，了解货物位置

**功能描述**：

- 支持货物的增删改查
- 货物独立建模，包含货物ID、名称、类型、重量、体积
- 货物与存储中心关联（每个货物属于一个存储中心，可动态调整）
- 系统预置演示数据（初始化时自动生成）
- **货物状态流程**：
    | 序号 | 场景 | 触发条件 | 状态更新 | 说明 |
    |---|---|---|---|---|
    | 1 | 货物初始在存储中心 | 订单创建，货物生成 | - → **待打包** | 初始状态为待打包 |
    | 2 | F007生成全局调度方案 | F007运行完成，货物被分配路径 | 待打包 → **待打包** | 状态不变，但货物已有路径信息（从哪个存储中心到哪个1级分拣中心到哪个0级分拣中心） |
    | 3 | 存储中心打包货物 | 同一包裹中的所有货物都**已有路径信息**（F007已分配路径） | 待打包 → **已打包** | 货物被打包成包裹，准备运输 |
    | 4 | F005分配包裹到车辆 | F005运行完成，包裹被分配给车辆 | 已打包 → **运输中** | 包裹开始运输 |
    | 5 | 货物运送到1级分拣中心 | 包裹到达1级分拣中心 | 运输中 → **待打包** | 货物需要重新打包成新的包裹（运往下一个层级） |
    | 6 | 1级分拣中心重新打包货物 | 同一包裹中的所有货物都**已送达**（到达1级分拣中心） | 待打包 → **已打包** | 货物被重新打包成新包裹（运往0级分拣中心） |
    | 7 | F005分配包裹到车辆 | F005运行完成，包裹被分配给车辆 | 已打包 → **运输中** | 包裹开始运输 |
    | 8 | 货物运送到0级分拣中心 | 包裹到达0级分拣中心（订单目标节点） | 运输中 → **已送达** | 货物送达，等待用户自提 |

**验收标准**：

* [ ] 用户可以通过表单新增货物，必填字段：货物名称、货物类型、重量、体积、存储中心ID
* [ ] 用户可以在货物列表查看所有货物，支持按存储中心筛选
* [ ] 系统初始化时自动生成不少于15种演示货物数据，随机分配到5个存储中心
* [ ] 货物状态按上述流程自动更新

**数据字段**：

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| goods_id | String | 唯一、非空、自动生成 | 货物编号（唯一） |
| goods_name | String | 非空 | 货物名称 |
| goods_type | String | 非空 | 货物类型（如电子产品、食品等） |
| weight | Float | 非空、>0 | 货物重量(kg) |
| volume | Float | 非空、>0 | 货物体积(m³) |
| node_id | String | 非空 | 所属节点ID（关联nodes表，此处为存储中心节点） |
| order_id | String | 非空 | 所属订单ID |
| status | Enum | 非空、默认"待打包" | 状态：待打包/已打包/运输中/已送达/异常 |
| created_at | DateTime | 自动生成 | 创建时间 |
| updated_at | DateTime | 自动更新 | 更新时间 |

##### F001-2 - 包裹管理（新增）

**用户故事**：

- 作为调度员，我希望能够查看包裹信息，了解包裹的运输状态
- 作为调度员，我希望能够手动重新打包包裹，以便优化运输

**功能描述**：

- 支持包裹的查看、手动重新打包
- 包裹是运输单位，包含多种货物
- 包裹有自己的属性（包裹ID、重量、体积、状态、发送地、接收地）
- 包裹仅用于一段节点间的运输，到达目的节点后根据全局调度结果重新打包
- **包裹状态流程**：
    | 序号 | 场景 | 触发条件 | 状态更新 | 说明 |
    |---|---|---|---|---|
    | 1 | F007生成全局调度方案 | F007运行完成，根据调度结果在节点中生成包裹 | - → **待打包** | 包裹初始状态为待打包 |
    | 2 | 节点打包货物 | 包裹中所有货物状态都为待打包 | 待打包 → **已打包** | 包裹打包完成，可以分配给车辆 |
    | 3 | F005分配包裹到车辆 | F005运行完成，包裹被分配给车辆 | 已打包 → **运输中** | 包裹开始运输 |

- **手动重新打包（repack）业务规则**：
    - 仅允许对状态为 `待打包` 的包裹执行 repack
    - 原包裹状态更新为 `异常`
    - 新包裹状态为 `待打包`
    - 重新打包的货物必须满足：
      1. 货物状态为 `待打包`（未分配）
      2. 货物处于同一个节点

**验收标准**：

##### F007 - 全局调度算法（新增，P0）

**用户故事**：

- 作为调度员，我希望系统能够根据订单和节点网络自动生成全局调度方案，确定每个货物的运输路径

**功能描述**：

- 基于规则评分+启发式算法，生成全局调度方案
- **算法选型**：用户可选择"传统算法"或"AI模型"，默认"自动"（传统算法）
- 输入：订单列表（含货物、0级分拣中心ID）+ 节点网络（存储中心、1级分拣中心的位置和容量）
- 输出：每个货物的运输路径（如"货物1：存储中心3 → 1级分拣中心A → 0级分拣中心27"）
- **注意**：F007输出后，系统自动调用F021（货物打包服务）一次性生成所有节点对（L0→L1和L1→L2）的包裹，存储在数据库，F005从数据库查询对应节点对的包裹进行调度。F007本身不包含打包逻辑。

**验收标准**：

* [ ] 用户点击"生成全局调度方案"按钮，系统在10秒内返回调度结果
* [ ] 调度结果满足硬约束：1级分拣中心容量不超限、同订单货物在同一1级分拣中心汇聚、最大存储时长不超限
* [ ] 调度结果考虑软约束：运输距离短、运输时间短、包裹数量小
* [ ] 前置条件：如果无待调度订单或无可用节点，系统提示"无法完成全局调度，没有待调度订单/没有可用节点"
* [ ] 如果无解（如1级分拣中心容量不足），系统提示"无法完成全局调度，请增加1级分拣中心容量或减少订单"

**输出数据字段**：

| 字段名 | 类型 | 说明 |
|---|---|---|
| schedule_id | String | 调度方案ID（唯一） |
| order_ids | Array | 关联的订单ID列表 |
| goods_schedules | Array | 每个货物的运输路径列表（含order_id、path数组） |
| total_distance | Float | 总运输距离(km) |
| total_time | Float | 总运输时间(分钟) |
| total_goods | Integer | 总货物数量 |
| score | Float | 调度方案评分（越小越好） |
| algorithm_type | String | 算法类型（传统/AI模型） |
| created_at | DateTime | 创建时间 |

**goods_schedules字段格式示例**：

```json
[
  {
    "goods_id": "G001",
    "order_id": "O001",
    "path": ["SC001", "SO001", "SO027"]
  },
  {
    "goods_id": "G002",
    "order_id": "O001",
    "path": ["SC001", "SO001", "SO028"]
  }
]
```

**注意**：F007输出后，系统自动调用F021（货物打包服务）一次性生成所有节点对（L0→L1和L1→L2）的包裹，存储在数据库，F005从数据库查询对应节点对的包裹进行调度。

**算法规则**：

- **评分公式**：`score = w1 × 总距离 + w2 × 总时间 + w3 × 包裹数`（分数越小越好）
- **默认权重**：`w1=0.5, w2=0.3, w3=0.2`
- **权重配置路径**：`algorithm_config.json` 中的 `global_schedule_weights` 字段
- **约束条件**：
    1. 1级分拣中心容量限制（包裹数量上限）
    2. 1级分拣中心最大存储时长限制
    3. 同订单货物必须在同一1级分拣中心汇聚
    4. 订单运输最大时长（P1，后续迭代更新）
- **算法流程**：
    1. 根据订单的0级分拣中心ID，确定每个订单的目的地
    2. 根据货物的存储中心ID，确定每个货物的起点
    3. **注意**：货物依赖于订单，不同订单中的同种货物是不同的，需要在数据中区分（通过goods_id+order_id组合唯一标识）
    4. 选择合适的1级分拣中心（考虑容量、距离、存储时长）
    5. 生成每个货物的运输路径（存储中心 → 1级分拣中心 → 0级分拣中心）
    6. 计算评分，优化方案

**验收说明**：验收以**约束满足、同输入可复现**为准，不要求全局最优。

##### F005 - 节点间调度算法（改造，P0）

**用户故事**：

- 作为调度员，我希望系统能够根据待运输包裹和车辆信息自动生成节点间调度方案，提高调度效率

**功能描述**：

- 基于规则评分+启发式算法，生成**层级间调度方案**
- **算法选型**：用户可选择"传统算法"或"AI模型"，默认"自动"（传统算法）
- **层级定义**：
    - 层级0：存储中心（货物运输起点）
    - 层级1：1级分拣中心（物流中心，货物分拣）
    - 层级2：0级分拣中心（快递站，用户自提）
    - 注意：一个层级中存在多个节点（如层级0有5个存储中心，层级1有2个1级分拣中心，层级2有50个0级分拣中心）
- **层级间调度**：负责两个相邻层级之间的调度方案（如层级0→层级1，或层级1→层级2）
- **调用次数**：F005会被调用2次，串行执行：
  1. 第一次调用：当前层级=0（存储中心），下一层级节点列表=所有1级分拣中心，输入包裹列表从数据库packages表查询（L0→L1节点对）
  2. 第二次调用：当前层级=1（1级分拣中心），下一层级节点列表=所有0级分拣中心，输入包裹列表从数据库packages表查询（L1→L2节点对）
- **两次串行调用规则**：
  1. **第一次 L0→L1**：输入 `packages`（from 属 L0、to 属 L1、状态已打包）；失败则**不执行第二次**。
  2. **第二次 L1→L2**：前置为第一次成功；包裹已到 L1 并重新「已打包」（演示可配置 `demo_mode=true` 跳过等待 F013-1）。
  3. **demo_mode**：默认 false；true 时允许连续两次 F005，仅用于课堂演示。
- 输入：待运输的包裹列表（从数据库packages表查询，对应from_node_id在当前层级、to_node_id在下一层级） + 车辆列表（属于当前层级的各个节点） + 下一层级的节点列表
- 输出：每个车辆分配的运输任务列表（JSON格式，包含vehicle_id、tasks数组）

**验收标准**：

* [ ] 用户点击"生成节点间调度方案"按钮，系统在10秒内返回调度结果
* [ ] 调度结果满足硬约束：车辆载重不超限、包裹不重复分配、包裹不遗漏
* [ ] 调度结果考虑软约束：距离优先（距离起始节点近的空闲车辆优先分配任务）、时效优先、车辆类型匹配、能源类型匹配
* [ ] 前置条件：如果无待运输包裹或无可用车辆，系统提示"无法完成节点间调度，没有待运输包裹/没有可用车辆"
* [ ] 如果无解（如车辆不足），系统提示"无法完成节点间调度，请增加车辆或减少包裹"

**输出数据字段**：

F005输出为JSON数组，每个元素代表一辆车的调度任务列表：

```json
[
    {
      "vehicle_id": "v001",
      "driver_id": "d001",
      "tasks": [
        {"from_node_id": "SC001", "to_node_id": "SO001", "package_ids": ["PKG001", "PKG002", "PKG003"]},
        {"from_node_id": "SO001", "to_node_id": "SC001", "package_ids": [], "is_return": true}
      ],
      "total_distance": 15.5,
      "total_time": 45.0
    }
]
```

字段说明：
- `vehicle_id`：车辆ID
- `driver_id`：司机ID
- `tasks`：任务列表，每个任务包含：
- `from_node_id`：起始节点ID（String类型，与nodes表node_id一致）
- `to_node_id`：目的节点ID（String类型，与nodes表node_id一致）
- `package_ids`：该任务分配的包裹ID列表（String类型）
- `is_return`：是否为返回任务，true表示车辆返回起始节点（可选，默认false）
- `total_distance`：总运输距离(km)
- `total_time`：总运输时间(分钟)

**算法规则**：

- **距离计算方式**：使用直线距离（Haversine公式），基于节点（latitude/longitude）的经纬度坐标计算（层级内 Haversine）
- **评分公式**：`score = w1 × 总距离 + w2 × 总时间 + w3 × 包裹数`（分数越小越好）
- **默认权重**：`w1=0.5, w2=0.3, w3=0.2`
- **权重配置路径**：`algorithm_config.json` 中的 `node_dispatch_weights` 字段
    1. 按包裹时效要求排序（紧急包裹优先）
    2. 按车辆载重匹配（大包裹配大车）
    3. 按距离评分（距离起始节点近的空闲车辆优先分配任务）
    4. 按车辆类型匹配（冷链包裹配冷链车）
    5. 按能源类型匹配（短途优先电动车）
- **车辆返回规则**：每个车辆的任务列表末尾自动追加一个 is_return=true 的返回任务

**验收说明**：验收以**约束满足、同输入可复现**为准，不要求全局最优。

##### F006 - 路径规划算法（改造，P0）

**用户故事**：

- 作为调度员，我希望系统能够为每辆车规划最优配送路线，降低配送成本

**功能描述**：

> - **P0 默认**：Haversine + 2-opt，不依赖高德（离线可演示）。
> - **P0 可选**：环境变量 `AMAP_ENABLED=true` 时调用高德；失败或超额降级 Haversine。

- 基于启发式算法（最近邻 + 2-opt），输出每辆车的全局配送路径
- 系统自动调用F006为F005生成的每一辆车的任务列表规划全局路径
- **输入**：F005生成的某一辆车的任务列表（包含车辆ID、任务序列：节点A→节点B→节点C...→返回节点A）
- **输出**：这辆车的全局道路路径（从起始节点到所有任务节点，再返回起始节点的完整道路路径坐标，包含经过的路段信息）

**验收标准**：

* [ ] 系统自动调用F006为每个车辆的每段路程规划路径，系统在10秒内返回规划结果
* [ ] 规划结果包含：车辆每段路程的具体道路路径坐标、总里程、总时间、碳排放
* [ ] 路径规划考虑约束：时效窗口、车辆载重、距离最小化、碳排放最小化
* [ ] 如果无解，系统提示"路径规划失败，请检查节点距离"

**输出数据字段**：

| 字段名 | 类型 | 说明 |
|---|---|---|
| route_id | String | 路线方案ID（唯一） |
| vehicle_id | String | 车辆ID |
| route_segments | JSON/Text | 道路路径路段信息（JSON数组，包含road_name、start_lng、start_lat、end_lng、end_lat） |
| total_distance | Float | 总里程(km) |
| total_time | Float | 总时间(分钟) |
| total_emission | Float | 总碳排放(kg) |
| algorithm_type | String | 算法类型（传统/AI模型） |
| created_at | DateTime | 创建时间 |

**算法规则**：

- **距离计算方式**：可选开启高德API（`AMAP_ENABLED=true`时调用，失败或超额降级Haversine）；P0默认使用Haversine距离（离线可演示）
- **优化目标**：最小化总成本 `cost = w1 × 距离 + w2 × 时间 + w3 × 碳排放`
- **默认权重**：`w1=0.4, w2=0.4, w3=0.2`
- **权重配置路径**：`algorithm_config.json` 中的 `route_planning_weights` 字段
    1. 基于Haversine距离最近邻算法生成初始路径
    2. 使用2-opt算法优化路径（交换任意两条边，可选调用高德API计算路径成本）
    3. 设置最大迭代次数，达到后返回当前最优解
    4. 考虑时效窗口约束（早到的订单往后排）
    5. 计算碳排放（燃油车：里程×0.2kg/km，电动车：0）

**验收说明**：验收以**约束满足、同输入可复现**为准，不要求全局最优。

#### 后端异常处理

| 异常类型 | 处理方式 | 返回码 |
|---|---|---|
| 参数校验失败 | 返回400，附带错误详情 | 400 Bad Request |
| 业务异常（如无解） | 返回200，business_code非0 | 200 OK |
| 系统异常（如DB错误） | 返回500，记录日志 | 500 Internal Error |
| DeepSeek API调用失败 | 降级处理，返回模拟数据 | 200 OK (with fallback) |
| AI模型加载失败 | 降级到传统算法，提示用户 | 200 OK (with fallback) |

#### DeepSeek API降级方案

- **场景1：API调用超时（>5秒）**
    - 降级策略：返回预设的模拟解释文本
    - 模拟文本："【系统提示】DeepSeek API调用超时，当前展示模拟数据。实际场景中，这里会显示AI生成的解释内容。"
- **场景2：API返回错误（如配额用尽）**
    - 降级策略：返回错误信息，提示用户
    - 错误信息："DeepSeek API调用失败，原因：{error_message}。请稍后重试或联系管理员。"
- **场景3：API返回内容不合理**
    - 降级策略：后端校验返回内容，不合理则重新调用（最多2次）
    - 如果2次都不合理，返回模拟数据

#### AI模型降级方案

- **场景1：模型加载失败（文件不存在或格式错误）**
    - 降级策略：使用传统算法，提示用户"AI模型加载失败，已自动切换到传统算法"
- **场景2：模型推理超时（>30秒）**
    - 降级策略：中断推理，使用传统算法，提示用户"AI模型推理超时，已自动切换到传统算法"
- **场景3：模型推理结果不合理（如约束不满足）**
    - 降级策略：使用传统算法，提示用户"AI模型推理结果不合理，已自动切换到传统算法"

#### 高德API异常处理

- **场景1：API限额用完（每日限额30万次地理编码/3000次路径规划）**
    - 处理方式（F006路径规划）：降级到初期算法（Haversine距离的2-opt）
    - 用户提示："API限额已用完，已自动切换到快速模式（不调用高德API）"
- **场景2：地理编码API调用失败（地址无效、网络异常）**
    - 处理方式：提示用户手动输入坐标
    - 用户提示："地址解析失败，请手动输入坐标（纬度、经度）"
- **场景3：路径规划API调用失败（网络异常、返回错误）**
    - 处理方式：提示用户重试
    - 用户提示："路径规划失败，请稍后重试"

#### 表关联关系

```
nodes（统一节点表）
  ├── storage_centers（通过node_id关联）
  ├── sorting_centers（通过node_id关联）
  ├── orders（destination_node_id）
  ├── goods（node_id）
  ├── packages（from_node_id, to_node_id）
  ├── vehicles（last_arrived_node_id, node_id）
  └── drivers（node_id）

global_schedules ──→ orders（关联订单ID）

node_dispatches ──→ vehicles（关联车辆ID）
                ──→ drivers（关联司机ID）
                ──→ routes（关联路线ID）
                （包裹ID存储在tasks JSON中，通过package_ids字段关联packages表）

routes ──→ node_dispatches（关联调度方案ID）
      ──→ vehicles（关联车辆ID）
      ──→ nodes（from_node_id, to_node_id）

historical_data ──→ orders（关联订单ID）
                ──→ vehicles（关联车辆ID）
```

**关联说明**：

- `nodes` 是统一节点表，所有节点（存储中心、分拣中心）的基础信息存储在`nodes`表中
- `storage_centers` 和 `sorting_centers` 通过`node_id`外键关联`nodes`表，只存储各自特有字段
- `goods` 关联 `orders`（多对一）和 `nodes`（多对一，原storage_center_id）
- `packages` 关联 `nodes`（多对多，from_node_id和to_node_id）和 `node_dispatches`（多对一，通过dispatch_id外键）
- `global_schedules` 关联 `orders`（多对多，通过order_ids JSON字段）
- `node_dispatches` 关联 `vehicles`（多对一）、`drivers`（多对一），包裹信息存储在tasks JSON字段中（package_ids关联packages表）
- `routes` 关联 `node_dispatches`（多对一）、`vehicles`（多对一）和 `nodes`（多对多，from_node_id和to_node_id）
- `drivers` 通过 `node_dispatches` 间接关联 `vehicles`，不直接关联
- `historical_data` 关联 `orders`（多对一）和 `vehicles`（多对一）

| 术语 | 英文 | 解释 |

| 运输任务 | Transport Task | 将包裹从一个节点运输到另一个节点的任务 |
| 异常 | Exception | 配送过程中发生的意外情况，如拥堵、车辆停留、包裹损坏等 |
| 重规划 | Re-planning | 异常发生后，重新进行全局调度和节点间调度 |
| 规则评分 | Rule Scoring | 一种启发式算法，通过预设规则对调度方案打分，选择总分最高的方案 |
| 启发式算法 | Heuristic Algorithm | 一种快速求解优化问题的方法，不保证全局最优，但能在可接受时间内得到较优解 |
| 强化学习 | Reinforcement Learning | 一种机器学习方法，通过与环境交互学习最优策略（如DQN） |
| 深度学习 | Deep Learning | 一种机器学习方法，使用多层神经网络学习数据表示（如MLP、LSTM） |

| LSTM | Long Short-Term Memory | 长短期记忆网络，一种循环神经网络，适合时间序列预测 |
| T+1批量计算 | T+1 Batch Calculation | 数据统计方式，基于前一天（T日）的数据，在第二天（T+1日）凌晨批量计算生成统计结果 |
