## 1. 总则

1. **可复现**：对方克隆仓库后，按文档能搭出与你一致的运行环境。
2. **及时记录**：新增依赖、环境变量、运行时版本要求，**当次开发内**写入对应配置文件并随代码一起提交。
3. **不分叉**：禁止「我本地装了包但 requirements / package.json 没更新」。
4. **API 契约**：接口格式以架构文档 §6 为准；有变更须同步对方并更新文档。

## 2. 环境配置文件一览

| 端 | 配置文件（须提交 Git） | 作用 |
| --- | --- | --- |
| 后端 | `src/backend/requirements.txt` | Python 第三方包及版本 |
| 后端 | `src/backend/.env.example` | 环境变量模板（无真实密钥） |
| 后端 | `src/backend/config/algorithm_config.json` | 算法权重等业务配置 |

**禁止提交**：`.env`、`node_modules/`、`.venv/`、`*.db`（见 [Git协作规范](./Git协作规范.md)）。

## 3. 后端依赖管理规范

### 3.1 权威文件

所有 Python 第三方包**只以** `src/backend/requirements.txt` 为准。

### 3.2 新增包的流程（必须遵守）

```text
1. 在 `src/backend/` 虚拟环境中安装
2. 将包名与版本范围写入 requirements.txt
3. 本地执行 pip install -r requirements.txt 验证可重装
4. 与代码变更同一 commit / 同一 PR 提交
```

**示例**：

```bash
cd src/backend
.venv\Scripts\activate          # Windows
pip install httpx

# 编辑 requirements.txt，新增一行：
# httpx>=0.27.0

pip install -r requirements.txt # 验证
```

### 3.3 版本写法

| 写法 | 含义 | 建议 |
| --- | --- | --- |
| `fastapi>=0.110.0` | 最低版本 | ✅ MVP 推荐 |
| `fastapi==0.115.0` | 固定版本 | 答辩前可锁定 |
| 无版本号 | 不推荐 | ❌ 避免 |

**不要**在未更新 `requirements.txt` 的情况下，仅在本地 `pip install`。

### 3.4 禁止做法

- ❌ 把虚拟环境 `.venv/` 提交到 Git  
- ❌ 只口头告诉对方「你装一下 xxx」  
- ❌ 使用 `pip freeze` 直接覆盖整个文件（会混入无关包）  
- ✅ 手动在 `requirements.txt` 增加一行并注明用途（可选注释）

### 3.5 requirements.txt 注释示例

```text
# Web
fastapi>=0.110.0
uvicorn[standard]>=0.27.0

# 认证
PyJWT>=2.8.0
passlib[bcrypt]>=1.7.4
```

## 4. 前端依赖管理规范

### 4.1 权威文件

- `src/frontend/package.json`：依赖声明  
- `src/frontend/package-lock.json`：版本锁定（**必须与 package.json 一并提交**）

### 4.2 新增包的流程（必须遵守）

```bash
cd src/frontend

# 生产依赖
npm install element-plus

# 开发依赖
npm install -D @types/node
```

`npm install` 会自动更新 `package.json` 和 `package-lock.json`。

**提交时两者都要 add**：

```bash
git add package.json package-lock.json
git commit -m "chore(frontend): 添加 element-plus 依赖"
```

### 4.3 禁止做法

- ❌ 只改 `package.json` 不跑 `npm install`、不更新 lock 文件  
- ❌ 提交 `node_modules/`  
- ❌ 手动改 `package-lock.json`（除非解决冲突）

### 4.4 对方如何同步你的新依赖

```bash
cd src/frontend
git pull
npm install
```

## 5. 环境变量规范

### 5.1 后端

| 文件 | 说明 |
| --- | --- |
| `src/backend/.env` | 本地真实配置，**不提交** |
| `src/backend/.env.example` | 模板，**提交**；新增变量时同步更新 |

**新增环境变量时**：

1. 在 `.env.example` 增加键名与说明（值用占位符）  
2. 在 `docs/环境配置说明.md` 补充说明（若影响启动）  
3. 群里通知前端是否需要配合  

### 5.2 前端

| 文件 | 说明 |
| --- | --- |
| `src/frontend/.env` / `.env.local` | 本地配置，**不提交** |
| `src/frontend/.env.example` | 模板，**提交** |

Vite 变量须以 `VITE_` 开头才能被前端读取。

## 7. 与 Git 工作流的关系

| 变更类型 | 须一同提交的文件 |
| --- | --- |
| 后端新功能依赖新包 | 业务代码 + `src/backend/requirements.txt` |
| 后端新环境变量 | 代码读取逻辑 + `src/backend/.env.example` +（必要时）环境配置说明 |
| 前端新 UI 库 | 业务代码 + `package.json` + `package-lock.json`（均在 `src/frontend/`） |
| 算法权重调整 | `src/backend/config/algorithm_config.json` |

**PR Review 检查项**：

- [ ] 是否新增了 import / npm import 但未更新依赖文件？  
- [ ] 是否新增了 os.getenv / import.meta.env 但未更新 `.env.example`？

## 8. 阶段开发检查清单

每个 MVP 阶段结束前，各自确认：

### 后端

- [ ] `pip install -r requirements.txt` 在干净虚拟环境中可成功  
- [ ] `requirements.txt` 无多余未使用包  
- [ ] `.env.example` 与代码读取的变量一致  
- [ ] README / 环境配置说明中的启动命令仍有效  

### 前端

- [ ] 删除 `node_modules` 后 `npm install` 可成功  
- [ ] `package.json` 与 `package-lock.json` 已提交  
- [ ] `.env.example` 与代码中 `import.meta.env` 一致
