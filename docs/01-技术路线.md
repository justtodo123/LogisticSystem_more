## 技术选型总览

| 层级 | 选型 | 理由 |
|------|------|------|
| **后端框架** | FastAPI (Python 3.13) | 同步/异步调用链并存，自动 OpenAPI，Pydantic 深度集成 |
| **ORM** | SQLAlchemy 2.0 + Alembic | 成熟稳定，迁移方案完善，支持 SQLite/PostgreSQL 无缝切换 |
| **数据校验** | Pydantic v2 | 请求/响应自动校验，AI 输出结构化校验层核心 |
| **前端框架** | Vue 3 + TypeScript | Composition API + `<script setup>`，组合式逻辑复用 |
| **UI 库** | Element Plus | 企业后台常用，组件丰富，Vue 3 原生支持 |
| **构建** | Vite | 毫秒级 HMR，Rollup 生产构建 |
| **数据库** | 开发 SQLite / P1 验证 PostgreSQL 16 | SQLite 零配置快速启动，P1 workflow 以 PostgreSQL 验证多 worker 场景；生产部署另行验收 |
| **缓存** | Redis + 有边界的进程内降级 | Redis 用于普通缓存和共享登录限流；关闭或故障时相关能力可降级，持久化幂等正确性以数据库为真相源 |
| **AI** | DeepSeek API | 自然语言→调度参数解析 + 方案解释/审查/异常分析；Pydantic 校验层把关 |
| **地图** | 高德 JS API v2.0 | 真实道路路径渲染 + Driving 路线规划；无 Key 自动降级 Canvas 折线 |

## 核心数据流（调度引擎）

```
unassigned 订单
    │
    ▼
[F007] 全局调度 draft（GlobalSchedule）
    │  参数：algorithm={greedy} + weights
    │  算法：GreedyGlobalScheduleStrategy
    │         ├─ L0：订单→仓储中心（就近）
    │         ├─ L1：仓储→分拣中心（容量+时窗）
    │         └─ L2：分拣中心→末端网点
    ▼
[F021] confirm → active
    │  打包（packaging）：同一路线订单→包裹
    │  生成 NodeDispatch ×N（按层级+车辆）
    ▼
[F005] 节点调度（NodeDispatch）
    │  车辆分配 → 多目标评分 → Top-K 候选
    ▼
[F006] 路径规划（RoutePlanning；2-opt 现为 stub）
    │  距离：真实路网 → 直线×系数 → Haversine 三档
    ▼
[F008] 模拟送达 → 异常检测 → 重规划（3策略）
```

## 技术边界与降级策略

| 外部依赖 | 正常 | 降级 | 触发条件 |
|----------|------|------|----------|
| DeepSeek API | AI 解析/解释/审查/分析 | 本地规则 + Pydantic 默认参数 | `DEEPSEEK_API_KEY=""` 或超时 |
| 高德地图 API | 真实道路路径渲染 + 距离/ETA | Canvas/SVG 折线 + Haversine 直线距离 | `MAP_API_KEY=""` |
| Redis | 普通缓存 + Redis 可用时共享登录限流 | 普通缓存与登录限流可按配置/故障降级；数据库持久化幂等不依赖 Redis | `REDIS_ENABLED=false` 或 Redis 故障 |
| SMTP/企业微信 | 业务事务写 transactional outbox，由独立 worker 至少一次尝试投递 | Console 渠道或 retry/dead-letter/manual_required | 渠道未配置或外部发送失败 |
| ERP Webhook | API Key 鉴权 | JWT 回退鉴权 | `ERP_API_KEY=""` |

- **可靠性**：CAS 状态抢占、数据库权威幂等（lease/claim token/原始响应重放）、原子号段、持久化 Replan Saga 与 transactional outbox；这些机制提供可恢复和至少一次边界，不声称 exactly-once
- **P1 验证拓扑**：PostgreSQL 16 + Redis 7 + 2 个 HTTP/Uvicorn workers + 1 个独立 outbox worker；8 workers 只属于 100,000 次编号 claim 的专项实验，不代表完整服务生产容量
- **可观测性**：request/trace/task ID、JSON 日志与 `/metrics`；完整 Grafana/Prometheus/OTel、跨 worker 指标聚合仍属后续
- **发布安全**：CD 构建后先生成 CycloneDX SBOM、扫描最终镜像并执行版本化 policy；CRITICAL/HIGH/UNKNOWN 或扫描异常 fail closed，门禁通过后才推固定 SHA tag，`latest` 仅为便利标签

- **后端**：pytest 等阶段性证据按日期、commit、场景记录在 [Claim-to-evidence 台账](../My_doc/delivery/02-claim-evidence-ledger.md)，不在本页固化易漂移的测试总数
- **CI/CD**：CI 覆盖 secret-scan、image-policy-test、migration-check、backend-test、p1-postgres-redis、frontend-check；CD 先 SBOM/Trivy 门禁，再发布固定 SHA 镜像
