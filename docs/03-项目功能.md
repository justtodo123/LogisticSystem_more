## 订单状态机

```
unassigned → assigned → in_transit → signed → exception
      ↓          ↓           ↓                     ↓
   closed     closed     exception  → assigned / in_transit / closed
```

| 状态 | 含义 | 可流转至 | 终态语义 |
|------|------|----------|----------|
| `unassigned` | 未分配（待调度） | assigned / closed | 可编辑、删除、关闭、纳入调度 |
| `assigned` | 已分配（已确认调度方案） | in_transit / closed | 可编辑、删除、关闭；尚未发运 |
| `in_transit` | 运输中（已开始配送） | signed / exception | 不可改单 |
| `signed` | 已签收（全部货物送达） | exception | 交付完成；若事后发现异常仍可转入 exception |
| `exception` | 异常 | assigned / in_transit / closed | 重规划恢复或关闭 |
| `closed` | 已关闭（取消/废弃） | - | 真正终态，不再流转 |

`signed` 与 `closed` 不可互换：前者是交付完成，后者是未完成即关闭。历史四态回填：`pending→unassigned`、`delivering→in_transit`、`completed→signed`（`completed` 不推断为 `closed`）。未知值不得静默映射成合法状态。

权威定义：`src/backend/core/order_status.py` + `ORDER_TRANSITIONS`。列表筛选只接受六态；前端/Mock/种子使用同一组值。货物 `delivered` 仍为货物终态，见 [plan 01](../My_doc/plan_todo/01-delivered-goods-replan-integrity.md)、[proced 010](../proced_problem/010-delivered-goods-reset-on-replan.md)。

## 调度核心流程

```
1. [F007] POST /api/schedule/global（或 AI parse）
   → draft 方案（GlobalSchedule + explanation_data）
   
2. [确认] POST /api/schedule/confirm/{schedule_code}
   → F021 打包（同一路线订单→包裹）
   → 生成 NodeDispatch ×N（按层级+车辆）
   → status: draft → active

3. [F005] 节点调度已在上两步中自动完成
   → 车辆分配 + 多目标评分 + Top-K 候选

4. [F006] POST /api/routes/plan
   → 路径规划（距离三档降级）

5. [F008] POST /api/simulation/deliver
   → 模拟送达 → 包裹状态推进
   → 异常检测 → POST /api/exceptions/{code}/replan（可选）
```
