> **生成时间**：2026-08-14
> **测试范围**：后端 FastAPI 全链路（83 个 API 端点、7 实体状态机、RBAC、调度引擎、AI 降级、中间件）
> **交付物**：`test_cases.txt`、`test_results.txt`、`issue_analysis.txt`（均在本目录）

## 一、测试执行概况

| 维度 | 结果 |
|------|------|
| 全量自动化测试 | `pytest` **635 passed / 0 failed**（100s） |
| 黑盒手势测试用例数 | 77 个（TC-001~TC-095） |
| 黑盒结果 | PASS 38 / FAIL 5 / BLOCKED 34 |
| 阻塞主因 | 真实种子数据缺乏可调度状态（无 unassigned 订单、无包裹、无调度记录） |

## 二、核心结论

**自动化测试全绿，但真实演示数据下暴露出 2 个 P0 阻断问题**，导致「按文档初始化后」的核心调度链路不可用：

1. **ISSUE-001（P0）**：`manager` 角色在 `ROLE_PERMISSIONS` 无映射 → 空权限，仓库类操作全部 403。
2. **ISSUE-002（P0）**：`init_demo_data.py` 种子订单用 `status="pending"`，而业务代码统一用 `unassigned`，导致：
   - AI 上下文待调度订单计数错误（100 → 0）；
   - 全局调度 F007 找不到可调度订单，返回 `40001 未找到未打包订单`。

> 注：本次发现 ISSUE-001 时，`admin` 账号本身也未在既有 DB 中种子化，重跑 `init_users.py` 后恢复。该现象与 `My_doc/plan_todo/README.md` 中已记录的 T-01（补建 admin 种子账号）同源，说明**部署初始化脚本的幂等/补建逻辑仍需在全新库上验证**。

## 四、建议的后续行动

1. **第一优先**：修复 ISSUE-002（种子状态改 unassigned）——它单点阻塞调度/打包/派单/路径全链路。
2. **第二优先**：修复 ISSUE-001（manager↔warehouse_operator 权限对齐）。
3. **第三**：ISSUE-003、005 回归完善。
4. **回归**：修复后在全新库上重跑 `init_users.py` + `init_demo_data.py`，再次执行第三阶段黑盒测试（重点是 TC-040 调度链路端到端）。
5. **遗留**：历史 README 记录的 4 项算法级边界（L1 容量检查维度、2-opt stub、load_rate 恒 0.5、deepseek 未实现）以及 Docker 构建验证（本机无 Docker）仍需另行排期。

## 五、风险提示

- 自动化测试夹具注入的数据与 `scripts/init_demo_data.py` 真实种子数据**存在状态枚举不一致**，导致「测试全绿但演示失败」的假象。建议补充一条**针对真实种子数据的冒烟测试**，避免回归。
- 本机 Windows 控制台 GBK 编码使中文 message 观测时乱码，不影响 API 语义，但在文字截图/日志取证时需注意。
