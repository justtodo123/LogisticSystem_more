# LogisticSystem 对标大厂后端校招 SP 的差距与优化路线图

> 文档类型：项目评审与优化建议  
> 评审日期：2026-08-24  
> 目标岗位：大厂后端开发校招（SP / SSP 冲刺）  
> 评审范围：后端架构、数据一致性、并发安全、性能容量、稳定性、安全、可观测性、测试、交付与项目表达  
> 说明：本文基于当前仓库的代码与已有验证记录进行静态评审；未执行生产环境压测，因此所有容量指标均为后续验收目标，不是当前实测结果。

## 1. 执行摘要

### 1.1 当前定位

LogisticSystem 已经不是简单 CRUD 项目。它具备较完整的物流领域模型、调度与重规划链路、JWT 鉴权、Redis 降级、AI 外部服务降级、审计、CI/CD、大量后端测试及本地业务 smoke。以普通校招项目衡量，其业务完整度和工程覆盖明显高于常见学生项目。

但如果按“大厂后端校招 SP 核心项目”衡量，当前最主要的问题不是功能数量不够，而是以下能力没有形成可验证闭环：

1. **并发正确性不足**：状态更新、幂等、编号生成和缓存存在竞态窗口。
2. **跨阶段一致性不足**：重规划流程内部多次提交，后阶段失败可能留下半成品。
3. **容量证据缺失**：没有真正的 HTTP 负载、压力、峰值及长稳测试。
4. **生产架构验证不足**：SQLite smoke 较充分，但 PostgreSQL、Redis、多 worker、Docker Compose 生产拓扑没有完整验收证据。
5. **RBAC 未真正落地**：权限表已定义，实际路由仍主要是“登录用户”和“dispatcher/admin”两档。
6. **可观测性不足**：缺少统一 trace/request/task ID、指标体系和关键业务链路追踪。
7. **故障恢复不足**：有局部 rollback 和降级，但缺少 Saga/outbox、持久化任务、补偿及恢复入口。
8. **技术结果不可量化**：索引和 N+1 优化已有局部证据，但缺少全链路性能、稳定性和架构优化前后数据。

### 1.2 综合评分（仅评价项目，不评价候选人整体）

| 维度 | 当前估计 | SP 参考 | 主要差距 |

## 2. 当前项目已有优势

### 2.1 业务链路完整

仓库已经覆盖订单、货物、包裹、车辆、司机、节点、调度、路线、异常、到货确认、重新调度、通知和报表等领域，且不是孤立 CRUD，而是存在跨实体状态流转。

适合在面试中重点展示：

- 调度 draft → confirm → 打包 → 节点调度 → 路径规划；
- 异常事件 → 影响范围分析 → partial/full/hybrid 重规划；
- 新旧方案版本关系及差异报告；
- delivered/signed 等终态保护；
- 主业务链路的本地 HTTP smoke 和重启持久化验证。

### 2.2 测试和工程基础较好

项目已有大量单元、API 和集成测试，并且已进行分页契约、N+1、状态一致性、回滚、鉴权、AI 降级等回归。路线查询已从循环查询改为常数级查询，证据见 [05-route-pagination-and-query-efficiency.md](../plan_todo/05-route-pagination-and-query-efficiency.md)。

CI 会运行后端 pytest 和前端构建，已有 Dockerfile、Compose 和镜像发布流程。相较只展示页面功能的学生项目，这些是明显优势。

### 2.3 已有稳定性意识

项目已具备：

- HTTP/参数异常统一转换；
- DeepSeek 缺失、超时或输出异常时降级；
- Redis 失败时回退进程内缓存；
- 请求级超时；
- 主要写操作的显式 commit/rollback；
- 通知失败不阻塞主业务；
- AI 建议需要人工确认。

后续优化应保留这些能力，并把“局部兜底”升级为“端到端可恢复”。

## 3. P0：必须优先解决的正确性问题

P0 的标准是：不解决就无法可信地声称系统具备生产级后端能力。建议先完成 P0，再建设压测；否则压测只会把竞态和半成品问题放大。

## 3.1 重构重规划事务边界

### 当前问题

完整重规划会连续执行创建方案、确认方案、版本记录、旧实体标记、节点调度和路径规划。相关编排集中在 [replan_service.py](../../src/backend/services/replan_service.py)。底层服务可能自行 `commit()`，导致：

- 前阶段成功提交，后阶段失败；
- 最外层 rollback 无法撤销已提交内容；
- API 返回失败，但数据库已经部分成功；
- 重试可能再次创建方案、包裹或路线；
- 运维无法判断任务应继续、补偿还是人工处理。

### 推荐设计

不建议不加分析地把所有阶段塞进一个长事务。应根据耗时与外部依赖选定以下一种方案：

#### 方案 A：单数据库短事务

适用于全部步骤都可快速、纯数据库完成的情况：

- 底层服务支持 `commit=False` 或完全不自行提交；
- 编排层统一 `with db.begin()`；
- 外部通知放到事务提交之后；
- 任何阶段失败时整个事务回滚。

#### 方案 B：Saga 状态机（更推荐用于长链路）

建立 `replan_tasks` 或等价任务表，至少包含：

- `task_code`；
- `source_schedule_id`；
- `target_schedule_id`；
- `status`：pending/running/compensating/succeeded/failed/manual_required；
- `current_step`；
- `idempotency_key`；
- `retry_count`；
- `last_error_code`；
- `created_at/updated_at`；
- 乐观锁版本号。

每一步必须满足：

- 可重复执行；
- 有明确前置状态；
- 有唯一幂等标识；
- 成功状态持久化；
- 已提交步骤有补偿或人工修复策略；
- 进程崩溃后能从数据库恢复。

### 验收标准

- 在 F007、F021、F005、F006 每个阶段注入异常；
- 验证数据库不会出现不可解释半成品；
- 同一任务重试不会重复生成包裹、批次或路线；
- 进程在任一步骤后终止并重启，任务可继续或进入明确的人工处理状态；
- 所有任务状态变化有审计记录。

## 3.2 为关键状态转移增加并发控制

### 当前问题

调度确认、到货确认、AI 建议确认/拒绝通常采用“读取当前状态 → 判断 → 修改 → 提交”。并发请求可能同时读取旧状态并都继续执行。

关键位置包括：

- 调度确认：[schedule_service.py](../../src/backend/services/schedule_service.py)
- 到货确认：[arrival_confirm_service.py](../../src/backend/services/arrival_confirm_service.py)
- AI 建议：[ai_suggestion_service.py](../../src/backend/services/ai_suggestion_service.py)

### 推荐设计

根据数据库和冲突概率选择：

1. **条件更新/CAS（优先）**
   - 示例语义：仅当 `status='draft'` 时更新为 `confirming`；
   - 检查 affected rows；0 行表示已被其他请求处理；
   - 再执行后续业务。
2. **SQLAlchemy 乐观锁**
   - 增加 `version`；
   - 使用 `version_id_col` 或显式 `WHERE id=? AND version=?`；
   - 冲突返回稳定业务码。
3. **数据库行锁**
   - PostgreSQL 使用 `SELECT ... FOR UPDATE`；
   - 锁范围应小，避免在持锁期间调用外部 API。

### 验收标准

- 20～100 个并发请求确认同一 draft，最多一个成功；
- 其余请求得到相同、可识别的冲突响应；
- 不产生重复包裹、重复事件和重复通知；
- PostgreSQL 下验证，不能只在 SQLite 下验证；
- 测试必须使用独立 Session/连接，不能在同一测试事务中伪造并发。

## 3.3 将幂等处理改为原子协议

### 当前问题

当前幂等中间件采用 check → execute → save，两个相同键的并发请求可能同时执行。相关实现见 [idempotency.py](../../src/backend/middleware/idempotency.py) 和 [idempotency_store.py](../../src/backend/utils/idempotency_store.py)。

异常分支再次调用下游请求的行为也需要移除，避免一次请求被执行两遍。

### 推荐设计

建立明确幂等状态：

```text
不存在 → PROCESSING → SUCCEEDED
                └→ FAILED/EXPIRED
```

实现方式可选：

- Redis `SET key value NX EX ttl` 原子占位；
- PostgreSQL 幂等记录表 + 唯一索引 + `INSERT ... ON CONFLICT`；
- 保存请求方法、路径、主体哈希、状态码、响应体和创建者；
- 同一个 key 搭配不同 payload 必须返回冲突；
- `PROCESSING` 请求返回 409/202 或按约定等待已有结果；
- 仅对明确的可重放响应缓存结果；
- 不应在错误处理器中重新执行完整业务。

### 验收标准

- 同 key、同 payload 并发 100 次，业务副作用只发生一次；
- 同 key、不同 payload 必须被拒绝；
- 多进程、多实例下仍成立；
- 原始 HTTP status、业务 code 和必要 header 能正确重放；
- 执行进程崩溃后，PROCESSING 状态可超时恢复。

## 3.4 修复编号生成竞态

### 当前问题

部分业务编码通过进程内序号、`max + 1` 或 `count + 1` 生成。多 worker 或并发事务可能生成相同编号。

相关算法模块包括：

- [global_schedule.py](../../src/backend/algorithms/global_schedule.py)
- [packaging.py](../../src/backend/algorithms/packaging.py)
- [route_planning.py](../../src/backend/algorithms/route_planning.py)
- [node_dispatch.py](../../src/backend/algorithms/node_dispatch.py)

### 推荐设计

优先级建议：

1. PostgreSQL sequence/identity；
2. UUIDv7/ULID；
3. 数据库号段表，通过原子 `UPDATE ... RETURNING` 分配；
4. 唯一约束作为最后防线，并对确定的唯一冲突做有限重试。

业务编码若需要日期前缀，可使用“日期 + sequence/ULID”，不要依赖查询当前最大值。

### 验收标准

- 多进程并发生成至少 10 万个编码，无重复；
- 所有业务编码仍有数据库唯一约束；
- 冲突不会转换成不明 500；
- 重试不会重复创建业务实体。

## 3.5 改造后台通知为可靠异步任务

### 当前问题

当前 fire-and-forget 任务可能复用请求作用域 Session，任务没有持久化，也没有可靠 drain。同步 SMTP 还可能阻塞事件循环。

### 推荐设计

优先采用事务 outbox：

1. 主业务事务中写业务数据和 outbox 事件；
2. 事务提交后 worker 拉取事件；
3. 每个事件有唯一键和投递状态；
4. 通知渠道按可重试/不可重试错误分类；
5. 指数退避、最大重试、死信和人工重放；
6. worker 自己创建数据库 Session；
7. SMTP、企业微信等阻塞/外部 I/O 不在请求事件循环中执行。

个人项目不一定必须引入 Kafka。可先使用 PostgreSQL outbox + 独立 worker；需要展示消息队列时再接入 Redis Streams、RabbitMQ 或 Kafka，并解释选型成本。

### 验收标准

- 主业务提交成功而通知暂时失败时，事件不会丢失；
- 重启 worker 后能继续处理；
- 重复消费不会重复发送，或具备明确的业务幂等键；
- 可查询积压量、失败量、重试量和最大延迟；
- 请求响应不受同步 SMTP 阻塞。

## 4. P1：达到 SP 项目说服力的核心升级

## 4.1 统一并真正落地 RBAC

### 当前问题

项目已经定义 `PERMISSIONS`、`ROLE_PERMISSIONS` 和 `require_permission()`，但实际路由主要仍使用 `get_current_user` 或 `require_dispatcher`。这导致声明权限与运行行为不一致，例如：

- `ai:use` 未真正限制 AI 接口；
- `audit:read` 未真正限制审计接口；
- manager/warehouse_operator 声明拥有的部分权限可能被 `require_dispatcher` 拒绝；
- 前端角色类型不完整，admin 可能被错误隐藏操作；
- ERP JWT 回退与普通认证的撤权语义不完全一致。

关键文件：

- [permissions.py](../../src/backend/core/permissions.py)
- [dependencies.py](../../src/backend/api/dependencies.py)
- [auth.ts](../../src/frontend/src/types/auth.ts)
- [router/index.ts](../../src/frontend/src/router/index.ts)

### 推荐设计

1. 确定角色与权限的唯一事实来源；
2. 所有业务路由按权限而不是粗粒度角色绑定；
3. 前端从 `/me` 获取权限集合；
4. 菜单、路由和按钮统一使用 `can(permission)`；
5. 后端始终作为安全边界，前端控制只改善 UX；
6. ERP JWT 回退复用标准用户查询、active 检查和当前权限判断；
7. 角色字段使用 enum/CHECK 或角色表约束；
8. 建立“所有非公开端点必须声明认证依赖”的自动测试。

### 验收标准

- 对每个权限参数化测试允许/拒绝矩阵；
- admin、dispatcher、viewer、manager、warehouse_operator 均有测试账号；
- 未知角色默认无权；
- AI、审计、导出、重规划等敏感端点符合最小权限；
- 前后端权限展示和后端执行结果一致。

## 4.2 完善 JWT 与登录安全

当前已有 bcrypt、JWT、数据库用户复查和 active 校验，但还缺少：

- 登录限流和失败次数控制；
- refresh token 或短期 access token；
- `jti`/token version；
- 单 token 或单用户会话撤销；
- issuer/audience；
- 密钥轮换；
- 真正的服务端 logout；
- 初始密码强制修改；
- 演示账号与生产环境隔离。

### 推荐最小实现

- access token 15～30 分钟；
- refresh token 轮换并只保存哈希；
- 用户表增加 `token_version`，必要时统一撤销；
- JWT 包含 `jti/iat/iss/aud`；
- 登录按 IP + 用户名限流；
- 失败次数和短期锁定写入 Redis；
- 测试用户禁用、删除、角色变更和 logout 后旧 token 行为；
- 正式环境禁止默认演示密码。

如果时间有限，也可以不实现完整 refresh token，但必须清楚说明安全边界和取舍。

## 4.3 统一错误契约和事务退出行为

### 当前问题

- HTTPException 与服务层 `error_response()` 可能分别使用真实 4xx/5xx 和 HTTP 200；
- 没有通用 `Exception` 全局处理器；
- 错误码存在硬编码和语义复用；
- 数据库依赖只 close，不统一 rollback；
- 文档中的 HTTP 错误格式与当前代码可能存在漂移。

相关文件：

- [main.py](../../src/backend/main.py)
- [error_codes.py](../../src/backend/core/error_codes.py)
- [response.py](../../src/backend/utils/response.py)
- [database.py](../../src/backend/config/database.py)
- [07-规范说明.md](../../docs/07-规范说明.md)

### 推荐设计

1. 建立领域异常基类，如 `DomainError`；
2. 领域服务抛稳定异常，不直接拼响应字典；
3. API 全局处理器统一映射 HTTP status、业务 code 和对外 message；
4. 参数错误、冲突、未找到、权限、限流、外部依赖、内部错误各有稳定语义；
5. 通用 Exception 对外隐藏内部细节，对内记录 traceback；
6. `get_db()` 在异常和取消时 rollback；
7. 禁止把 `str(e)`、SQL 或第三方完整响应直接返回客户端；
8. 自动测试代码、文档和错误码唯一性。

建议 HTTP 语义与业务码并存：HTTP status 供网关/APM/通用客户端使用，业务 code 供前端和领域逻辑精确识别。

## 4.4 增强缓存一致性与防护

### 当前问题

项目已有 Redis → 内存降级，但需要进一步验证和修复：

- `_redis_usable` 状态赋值是否正确修改模块级变量；
- 裸 dict 在复合操作下的并发安全；
- 同一热点 key 失效后发生 cache stampede；
- 多 worker 的内存缓存互不一致；
- 降级后不能把内存缓存当作强一致存储；
- 缓存失效与数据库提交顺序是否可靠。

关键文件：[cache.py](../../src/backend/utils/cache.py)。

### 推荐设计

- cache-aside 只缓存允许短暂不一致的查询；
- 写操作先提交数据库，再删除缓存；
- 对热点 key 使用 singleflight/分布式锁或逻辑过期；
- TTL 增加随机抖动，避免集中失效；
- 空值短 TTL 防穿透；
- 限制 key 数量和对象大小；
- Redis 故障采用熔断窗口，不要每次请求反复探测；
- 输出命中率、回源率、淘汰量和降级率；
- 明确多实例降级时的一致性限制。

## 4.5 建立真正的性能与容量测试

### 当前证据边界

目前已有：

- 1000 行 SQLite 分页查询的平均耗时回归；
- 路线分页查询次数/N+1 回归；
- 串行业务 smoke。

这些不能证明系统并发容量。仓库未发现 Locust、k6、JMeter 或等价系统级负载模型。

### 推荐测试体系

建议选择 k6 或 Locust。Python 项目若重视场景编排可优先 Locust；若重视 CI、阈值和低资源压测客户端可选 k6。

至少建设以下场景：

| 场景 | 目的 | 核心指标 |
|---|---|---|
| 登录与 `/me` | 认证基线 | RPS、P95/P99、失败率 |
| 订单/路线分页查询 | 高频读 | RPS、缓存命中、DB QPS、慢查询 |
| 创建/更新订单 | 常规写 | TPS、锁等待、冲突率 |
| 同一 draft 并发确认 | 竞态验证 | 成功数必须为 1、重复副作用为 0 |
| 全局调度 | CPU/DB 混合慢接口 | P95、任务耗时、队列长度 |
| 异常重规划 | 长链路稳定性 | 成功率、补偿率、恢复时间 |
| Redis 故障 | 降级容量 | 降级率、DB 增量、错误率 |
| 外部 AI 超时 | 舱壁与超时 | 请求堆积、线程/连接占用 |
| Spike | 突发流量 | 恢复时间、错误峰值 |
| Soak 2～8 小时 | 泄漏与稳定性 | RSS、连接数、FD、延迟漂移 |

### 环境要求

- PostgreSQL，而不是只用 SQLite；
- Redis 开启；
- Nginx/反向代理；
- Uvicorn 多 worker；
- 固定 CPU、内存、数据库规格；
- 固定数据规模，例如 10 万/100 万订单；
- 压测客户端与服务端尽量分离；
- 保存脚本、配置、原始 JSON/CSV 和报告。

### 建议门禁

门禁值必须在基线实测后确定，不应先编造高 RPS。初始可先采用相对门禁：

- 错误率小于 1%；
- 无未预期 5xx；
- P95 相比基线退化不超过 15%；
- 并发状态转移不产生重复副作用；
- 两小时 soak 中 RSS 无持续单调增长；
- 数据库连接池无长期耗尽；
- 慢查询数量和锁等待有明确上限。

最终报告必须包含硬件、软件版本、worker 数、数据规模、请求分布、预热、持续时间和结果分位数。

## 4.6 建立可观测性闭环

### 当前缺口

日志较分散，缺少统一贯穿的：

- request ID / trace ID；
- 用户和权限决策上下文；
- replan task ID；
- 幂等 key；
- 调度方案和批次 ID；
- 阶段耗时；

### 推荐建设

1. OpenTelemetry 采集 HTTP、SQLAlchemy、Redis、httpx；
2. 结构化 JSON 日志；
3. Prometheus 指标；

5. request ID 与业务 task ID 注入日志上下文；
6. 敏感字段脱敏；

## 5. P2：进一步提升到优秀 SP 项目

## 5.1 PostgreSQL 生产化

当前开发默认 SQLite。建议将 PostgreSQL 作为生产验收基线，并系统处理：

- 连接池容量与超时；
- transaction isolation；
- deadlock/serialization failure 的有限重试；
- `FOR UPDATE`/SKIP LOCKED 的适用场景；
- EXPLAIN ANALYZE；
- 复合/部分索引；
- keyset pagination；
- 迁移向前、回滚及大表变更；
- 备份恢复演练。

不要为了“技术栈丰富”引入分库分表。只有在压测证明单库瓶颈、数据规模和访问模式合理时再讨论读写分离、分区或分片。

## 5.2 调度算法性能和可解释性

现有文档记录的算法边界包括：

- L1 容量检查维度问题；
- 2-opt 仍为 stub；
- load_rate 跨候选近似恒定；
- `algorithm=deepseek` 仅缓解，未实现真实策略。

见 [08-优化点说明.md](../../docs/08-优化点说明.md)。

建议：

- 修复已知算法语义问题；
- 建立 100/1,000/10,000 订单数据集；
- 记录运行时间、内存、约束违反率、总里程、成本和 SLA；
- 对比 greedy、2-opt、OR-Tools/VRP 或其他明确基线；
- 做消融实验解释每项约束和评分权重的效果；
- 将 CPU 密集调度从请求事件循环移出，改为任务队列或进程池；
- 为超时任务提供取消、进度和结果查询。

SP 面试价值不在于宣称算法“智能”，而在于能给出基线、复杂度、权衡和真实实验结果。

## 5.3 CI/CD 和发布治理

现有 CI/CD 是良好起点，但建议补充：

- Ruff/Black/mypy 或项目选择的等价静态检查；
- 依赖漏洞和 secret scan；
- Alembic migration 检查；
- PostgreSQL + Redis 集成测试；
- Docker 镜像构建与启动 smoke；
- SBOM、固定基础镜像版本和非 root 用户；
- 部署后健康检查与回滚；
- 性能测试定期任务，而非每个 PR 都运行完整压力测试；
- 测试报告、覆盖率、压测结果和镜像扫描 artifact。

当前 Compose 业务 E2E 尚需按 [02-docker-seed-e2e.md](../plan_todo/02-docker-seed-e2e.md) 完成真实 Docker 环境验收。

## 5.4 测试结构升级

保留现有测试数量优势，重点补充缺失类型：

1. PostgreSQL/Redis Testcontainers 集成测试；
2. 独立 Session 的并发竞态测试；
3. Hypothesis 属性测试，用于状态机和输入边界；
4. 故障注入：超时、断连、commit 前后异常、worker 重启；
5. Saga/outbox 恢复和重复消费测试；
6. migration 从旧版本升级测试；
7. API 契约测试；
8. 性能基线与查询计划回归；
9. 安全测试：越权、过期/篡改 token、限流、输入体积、CSV/Excel 导入边界；
10. 端到端环境 smoke。

测试目标不应只追求数量和覆盖率，应覆盖最危险的状态空间。

## 8. SP 面试应准备的系统设计问题

完成优化后，应能不依赖背稿回答以下问题：

### 并发与一致性

1. 两个请求同时确认同一个 draft 会发生什么？
2. 为什么选择乐观锁、条件更新或悲观锁？
3. 同一个幂等键在两个 worker 上同时到达如何保证只执行一次？
4. 唯一约束冲突时为什么不能简单无限重试？
5. SQLite 和 PostgreSQL 的并发语义有何差异？

### 事务与消息

1. 重规划为什么不适合一个超长数据库事务？
2. Saga 的每个补偿动作是什么？
3. 进程在第五阶段崩溃后如何恢复？
4. 为什么 outbox 能解决数据库提交成功但消息发送失败？
5. 消息重复消费如何幂等？

### 性能

1. 系统稳定容量是多少，测试环境是什么？
2. P95/P99 为什么比平均值更重要？
3. 数据库、缓存、算法和外部 API 各自占多少耗时？
4. 缓存失效后如何防止击穿？
5. 如何判断增加 worker 仍能提升吞吐？

### 安全与权限

1. 为什么前端隐藏按钮不等于权限控制？
2. 角色变化后旧 token 如何处理？
3. ERP API key 和用户 JWT 的授权语义有何不同？
4. 审计日志为什么应限制读取权限？
5. 如何防止默认账号进入生产？

### 可观测性和故障恢复

1. 一次重规划失败如何定位到具体阶段？
2. 如何区分业务失败、系统失败和外部依赖失败？
3. 发生部分成功时告警和人工恢复入口是什么？
4. 如何判断 Redis 降级正在拖垮数据库？
5. soak 测试如何发现连接或内存泄漏？

## 9.1 当前可以真实陈述

- 构建 FastAPI + SQLAlchemy 的物流调度后端，覆盖订单、包裹、节点调度、路线规划、异常重规划等业务链路；

- 建立 JWT 鉴权、审计、CI/CD 和 Docker 化基础。

## 9.2 尚不能无证据陈述

在完成对应验证前，不应写：

- “支持高并发”；
- “达到生产级”；
- “支持百万级订单”；
- “系统 QPS 达到某数值”；
- “保证 exactly-once”；
- “通过压力测试”；
- “完整 RBAC”；
- “分布式事务完善”；
- “微服务架构”。

应使用准确措辞，例如：

- “实现异步 API，并正在通过 CAS、原子幂等和 PostgreSQL 并发测试补齐业务并发安全”；
- “已完成 SQLite 小规模查询回归，系统级 k6/Locust 容量测试待建设”；
- “定义了细粒度权限模型，当前生产路由仍以登录/dispatcher 两级鉴权为主”。

## 9.3 最有价值的 STAR 故事

建议最终准备三个可量化故事：

1. **并发确认重复副作用**
   - 发现 check-then-act 竞态；
   - 使用 CAS/乐观锁改造；
   - 100 并发请求最多一次成功；
   - 无重复包裹和通知。
2. **重规划部分成功**
   - 识别多次提交导致回滚失效；
   - 设计 Saga/outbox；
   - 逐阶段故障注入；
   - 任务可恢复且状态可观测。
3. **查询与容量优化**
   - N+1/慢查询基线；
   - join、索引、缓存或分页优化；
   - 展示优化前后 SQL 次数、P95/P99、数据库 CPU 和吞吐变化。

这些故事比继续增加普通页面更有 SP 面试价值。

## 11. 最终建议

项目下一阶段应停止横向堆叠普通功能，集中完成以下技术闭环：

> **并发正确性 → 事务/Saga → 可靠消息 → PostgreSQL 生产拓扑 → 可观测性 → 可复现压测 → 量化优化报告**

最优先的三个改造是：

1. **调度确认、到货确认和 AI 建议的原子状态转移；**
2. **重规划 Saga/事务边界及故障恢复；**
3. **k6/Locust + PostgreSQL + Redis + 多 worker 的真实容量验证。**

完成这些后，项目的竞争力提升主要来自“能够证明系统在并发、故障和容量条件下仍然正确”，而不是来自更多 API 数量。这正是普通完整项目与大厂后端 SP 项目的核心分界。
