## AI 执行约定

本计划面向 AI 执行时遵循以下约定：

1. **每个任务卡片的"涉及文件"表 = 操作清单**。`新建`/`修改`/`删除` 三种操作，按顺序执行
2. **"实施步骤"中的代码片段 = 目标形态**。AI 应理解意图并适配到实际代码风格
3. **执行每个任务前先读取涉及的所有现有文件**，确认当前状态与计划一致
4. **每完成一个任务运行相关测试**：`pytest -m unit -x` 确保不引入回归
5. **验收标准 = 测试用例**。每个 checkbox 就是一条验证指令
6. **遇到计划与实际代码冲突时**：先报告差异，再征求确认后调整

## 中断恢复协议

> **核心原则**：每次中断都能从上一个"安全点"无损恢复，不需要猜测"上次做到哪了"。

---

### 一、五层保障体系

```
┌──────────────────────────────────────────────────┐
│  Layer 1: Git 分支隔离    ← 中断不污染主分支        │
│  Layer 2: 小步提交        ← 每个文件改动独立 commit  │
│  Layer 3: 任务追踪文件    ← 实时记录进度状态         │
│  Layer 4: 测试闸门        ← 通过测试才算完成         │
│  Layer 5: 可逆迁移        ← alembic 支持 upgrade/downgrade │
└──────────────────────────────────────────────────┘
```

---

### 二、Layer 1：Git 分支策略

每个任务在**独立分支**上执行，中断后分支保留所有半成品代码：

```
main ──────────────────────────────────────────────
        \
         develop ─────────────────────────────────
                  \
                   task/T0-1-env-config ── ✅ 完成，合并到 develop
                   task/T0-2-rbac ──────── ⚠️ 中断，分支保留现场
                   task/T0-3-audit ─────── ⬜ 尚未开始
```

**规则**：
| 场景 | 操作 |
|------|------|
| 开始执行任务 T{X}-{N} | `git checkout develop && git checkout -b task/T{X}-{N}-{slug}` |
| 任务完成（验收全通过） | `git checkout develop && git merge task/T{X}-{N}-{slug}` |
| 任务中断（未完成） | 分支保留不动，TASK_TRACKER.md 记录中断点 |
| 恢复中断任务 | `git checkout task/T{X}-{N}-{slug}`，读取 TRACKER 定位断点 |
| 放弃中断任务 | `git checkout develop && git branch -D task/T{X}-{N}-{slug}` |

**为什么不用 stash？** Stash 是栈结构，多个中断会覆盖。Feature branch 是持久化的，断电/重启/换机器都不会丢。

---

### 三、Layer 2：小步提交

每个**文件改动**独立提交，而非每个任务一个提交。

```
任务 T0-2（RBAC 权限）为例：
  commit 1: "feat(T0-2): add permissions.py with role matrix"
  commit 2: "feat(T0-2): extend User model with permissions field"
  commit 3: "feat(T0-2): add require_permission dependency"
  commit 4: "feat(T0-2): wire permissions into schedule/order APIs"
  commit 5: "feat(T0-2): add alembic migration for user permissions"
  commit 6: "test(T0-2): add permission test cases"
```

**好处**：即使在第 4 步中断，前 3 个 commit 已经是干净的、可回滚的增量。恢复后从第 4 步继续，无需重做 1-3。

---

### 四、Layer 3：任务追踪文件

创建 `My_doc/TASK_TRACKER.md`，记录 23 个任务的实时状态。

**格式**：
```markdown
## 进度追踪

> 最后更新：2026-08-07 15:30
> 当前任务：T0-2（权限 RBAC）
> 当前分支：task/T0-2-rbac

| 任务 | 状态 | 分支 | 完成步骤 | 备注 |
|------|------|------|----------|------|
| T0-1 | ✅ done | task/T0-1-env-config | 5/5 | merged to develop |
| T0-2 | 🔄 in_progress | task/T0-2-rbac | 3/6 | 权限中间件完成，API 注入进行中 |
| T0-3 | ⬜ pending | — | 0/3 | — |
| ... | ... | ... | ... | ... |
```

**恢复时 AI 的读取顺序**：
1. 读 `TASK_TRACKER.md` → 找到第一个 `in_progress` 任务
2. `git checkout` 对应分支
3. 读最后一个 commit message → 确定断点
4. 继续执行

---

### 五、Layer 4：测试闸门

每个任务完成时**必须先跑测试再标注完成**。测试不通过 = 任务未完成 = 不可合并到 develop。

```bash
# 单任务完成后的验证流程
pytest -m unit -x -q        # 单元测试快速失败
pytest -m integration -x -q  # 集成测试
# → 全部通过 → 标注 ✅ done → merge 到 develop
# → 有失败 → 标注 🔄 in_progress → 修复 → 再测
```

**中断恢复时**：`git checkout task/xxx` 后先跑 `pytest -m unit -x`，确认当前代码状态。

---

### 六、Layer 5：Alembic 迁移安全

数据库迁移是最容易"中断后状态混乱"的操作。每项规则：

| 规则 | 说明 |
|------|------|
| **迁移单独一个 commit** | 不和业务代码混在同一 commit |
| **必须可逆** | 每个 `upgrade()` 配 `downgrade()` |
| **执行前备份** | `cp data/logistics.db data/logistics.db.bak` |
| **中断后检查** | `alembic current` 查看当前版本，与预期对比 |
| **回滚方式** | `alembic downgrade -1` 回到上一个版本 |

**恢复示例**：
```
场景：执行 alembic upgrade 时中断，不确定迁移是否生效
恢复步骤：
  1. alembic current                    # 查看当前版本号
  2. alembic history                    # 查看迁移历史
  3. 若新版本已生效 → 继续写业务代码
  4. 若未生效 → 重新 alembic upgrade head
  5. 若半生效（极罕见）→ alembic downgrade -1 && alembic upgrade head
```

```
│ 5. 从断点继续   │

```

### 八、常见中断场景速查

| 场景 | 判断方法 | 恢复动作 |
|------|----------|----------|
| **AI 会话断开** | 重开对话，读 TRACKER | git checkout 分支 → 读 log → 继续 |
| **代码写了一半** | `git status` 有未提交文件 | 审查 diff → 补完或 git stash（记录到 TRACKER） |
| **数据库迁移半执行** | `alembic current` vs 预期版本号 | 对照 Layer 5 流程处理 |
| **测试跑到一半失败** | `pytest -x` 快速验证 | 修 bug → 补测试 → 再跑 |
| **合并冲突** | `git merge` 报 CONFLICT | 手动解决 → `git add . && git commit` |
| **完全忘了做到哪** | TRACKER 也丢了 | `git branch --list 'task/*'` → `git log --oneline task/xxx` 反推 |

### 九、TRACKER 文件维护规则

- **开始任务时**：状态改为 `🔄 in_progress`，记录分支名
- **完成一个步骤时**：更新 `完成步骤` 计数
- **遇到阻塞时**：状态改为 `🚫 blocked`，在备注写阻塞原因
- **任务完成时**：状态改为 `✅ done`，记录 merge commit hash
- **每次更新 TRACKER 后**：`git add My_doc/TASK_TRACKER.md && git commit -m "chore: update task tracker"`
