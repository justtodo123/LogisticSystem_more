# 00A — 文档基线校准与状态源治理

## 来源证据与当前行为

- [plan_todo README](./README.md)同时包含活动路线图、T-01～T-13历史收尾和旧测试基线，读者无法稳定区分当前状态与历史事实。
- [TASK_TRACKER](../post_plan/TASK_TRACKER.md)仍以“23 / 23”作为总体完成状态，但其最后更新日期为 2026-08-10，且“done”按当时的 develop 合并口径定义；它不能代表当前生产就绪度。
- [优化实施计划](../post_plan/优化实施计划.md)和 [开发执行计划](../post_plan/开发执行计划.md)保留了历史提案及执行设计，其中未勾选项与后来已完成项并存，不能直接作为当前待办统计。
- 多份当前入口文档仍写 `626` 个测试；已知验证基线为 2026-08-19 在 `src/backend` 执行 `python -m pytest -q` 得到 `635 passed`，前端类型检查随构建通过。
- [docs/03-项目功能](../../docs/03-项目功能.md)和 [docs/07-规范说明](../../docs/07-规范说明.md)仍把到货确认描述为公开端点，实际实现已经要求 dispatcher/admin；订单前后端仍存在六态与旧四态漂移。
- Docker 配置存在不等于 Docker 业务 E2E 已验证；当前机器没有 Docker，因此该能力仍应标记为 `blocked`/待外部证据。
- [docs/08-优化点说明](../../docs/08-优化点说明.md)混合已修复项和仍存在的 L1 容量、2-opt、load_rate、DeepSeek 策略边界，缺少逐项的当前状态、日期和证据。

## 问题与目标

建立可追溯的文档事实基线，消除过时记录、相互矛盾的描述和缺失的完成证据；在不改写历史结论的前提下，让后续计划、当前规范和代码验证使用同一套状态来源。

## 范围

- 计划文档和状态源的分类、读取顺序、状态字段与依赖关系。
- 当前入口文档中的测试基线、API/权限、订单与货物状态、Docker 验证级别、算法边界和完成证据。
- 历史 tracker/计划的历史标识、当前路线图指针和必要的冲突注记。
- owner、日期、Commit/PR、验证命令/结果、环境和残留问题的缺漏补齐。

## 非目标

- 本计划不直接修复业务代码、数据库数据或前端实现。
- 不把历史 `626` 测试里程碑静默改写为 `635`；历史数字保留其当时日期和语境，当前数字必须带验证日期与命令。
- 不因文件存在、CI 配置存在或本地静态检查通过而宣称 Docker、远端、真实库或完整业务 E2E 已验收。
- 业务语义未决时不自行选择方案；应将计划标为 `needs_decision` 并链接决策记录。

## 文档分类与唯一状态源

| 分类 | 规则 | 本仓库代表文件 |
|------|------|----------------|
| 当前规范/当前状态 | 必须与当前代码、已执行验证和已批准决策一致；改动同步日期和证据 | `My_doc/plan_todo/README.md`、`docs/README.md`、`docs/03-项目功能.md`、`docs/07-规范说明.md` |
| 历史快照 | 保留当时事实，不回填成当前事实；顶部增加历史日期和当前入口链接 | `My_doc/post_plan/TASK_TRACKER.md`、`My_doc/post_plan/优化方案.md`、`My_doc/post_plan/优化实施计划.md`、`My_doc/post_plan/开发执行计划.md`、README 中 T-01～T-13 段落 |
| 决策记录 | 记录选项、结论、日期、影响和后续任务，不承担实时完成率 | `My_doc/plan_todo/04-time-window-contract-decision.md` 及后续新增决策记录 |

`My_doc/plan_todo/README.md` 是唯一实时状态聚合入口；各计划卡是对应任务的细粒度状态源。历史文件只能用于追溯，不能再声称自己是实时 tracker。

## 事实矩阵（必须逐项有来源）

| 事实域 | 当前记录要求 | 已知冲突/缺口 |
|--------|--------------|----------------|
| 测试基线 | 命令、目录、日期、通过/失败/警告数 | `626`历史里程碑与当前 `635 passed` 混用 |
| API 与权限 | 路由、角色、当前代码引用和契约文档 | 到货确认“公开”描述过时，实际为 dispatcher/admin |
| 状态契约 | 订单六态、货物终态、前端/Mock/种子值 | 后端六态与前端旧四态漂移；delivered 重规划问题仍未修 |
| 部署验证 | 配置存在、镜像构建、Compose 启动、业务 smoke 分级记录 | Docker 当前无本地证据，不能写成已验收 |
| 算法能力 | 已实现、短期缓解、stub、未实现分别列出 | 2-opt、load_rate、L1、DeepSeek 边界混在完成描述中 |

## 有序实施步骤

1. **冻结来源清单**：逐份标记当前规范、历史快照和决策记录，记录最后更新日、责任人和权威来源；建立本计划所列事实矩阵。
2. **治理状态入口**：将 `plan_todo/README.md` 明确为唯一实时状态源；加入当前验证日期、活动计划依赖图、状态图例和历史入口；为历史文件增加醒目标识与回链。
3. **校准当前文档**：按“代码/实际验证证据 → 当前决策记录 → 实时路线图 → 历史快照”的顺序修正过时或矛盾描述，重点处理 `626/635`、权限、状态、Docker 和算法边界。
4. **补齐记录缺漏**：为每个活动计划补 owner（未知则保留“待认领”）、更新时间、进入条件、验收命令、Commit/PR、环境、结果和残留项；不凭空填写未知事实。
5. **一致性复查**：搜索重复事实和旧状态措辞，检查 Markdown 链接、计划 ID、依赖无环、状态不越级；保留历史数字和历史完成结论的时间语境。
6. **形成治理收尾**：在本卡填写实际完成记录，更新 README 状态和事实矩阵版本；未解决的业务问题继续由 01～05 处理，不在本卡关闭。

## 验收标准

- `README.md` 是唯一明确的实时状态聚合入口，历史 tracker/计划均有历史标识和回链。
- 00A 与 00～05 的 plan_id 唯一、状态合法、依赖无环；`00A` 完成前 01 不得标记 `done`。
- 当前文档中的测试基线写明命令、目录和日期；历史 `626` 仍可追溯但不再被表述为当前基线。
- 到货确认权限、订单/货物状态、Docker 验证级别和算法实现边界与代码/验证证据一致；未知或未决内容显式标为待验证/`needs_decision`。
- 每项活动任务均有 owner、updated、进入条件、验收标准和真实完成记录；未执行的外部验证不得填写为通过。
- 全仓 Markdown 链接可解析，文档没有把 `blocked`、`needs_decision` 或 `mitigated` 折算为 `done` 的表述。
