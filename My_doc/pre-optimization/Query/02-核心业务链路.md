# 二、核心业务链路

> 覆盖订单调度、打包、节点间运输、路径规划以及方案生命周期。

### Q04：请完整描述订单从调度到路径规划的主链路。

- 难度：中
- 核心代码：
  - `src/backend/services/schedule_service.py:101-180`
  - `src/backend/services/dispatch_service.py:107-160`
  - `src/backend/services/route_service.py:24-115`
  - `src/frontend/src/views/Dashboard.vue:32-84`

#### 参考回答

主链路分三段：全局调度、节点间调度、路径规划。首先 `ScheduleService.create_global_schedule()` 执行 F007，选择每票货物的 L0→L1→L2 路径，生成 `draft` 调度方案；确认后执行 F021 打包并推进订单/货物状态。然后 `DispatchService.create_node_dispatch()` 调用 F005，根据包裹和车辆资源生成 `dispatch_batches` 与 `node_dispatches`，并把包裹、货物、车辆、司机推进到运输状态。最后 `RouteService.create_route_planning()` 针对每条车辆调度明细执行 F006，生成 `routes` 和 `route_segments`。

前端 `Dashboard.vue` 将这个链路拆成多个 composable：`useGlobalSchedule` 管理预览和确认，`useNodeDispatch` 管理节点调度，`useRouteVisualization` 管理路线规划和展示，`useSimulationDelivery` 管理模拟送达。这说明前端没有把所有业务状态堆在一个组件里，而是按业务子流程组合。

从业务一致性看，链路的关键是串行依赖：没有全局方案就不能节点调度，没有节点调度就不能路径规划；F005 的输出是 F006 的输入。这也解释了为什么 Service 层承担编排职责，而不是让前端随意拼接算法接口。

### Q05：为什么调度方案采用“预览 draft → 确认 active”的两阶段提交体验？

- 难度：中
- 核心代码：
  - `src/backend/services/schedule_service.py:129-170`
  - `src/frontend/src/composables/useGlobalSchedule.ts:117-164`
  - `src/frontend/src/views/Dashboard.vue:160-190`

#### 参考回答

后端在 `preview=True` 时只执行 F007 并保存 `GlobalSchedule(status='draft')`，不立即打包、不更新订单状态。前端生成预览后显示“确认采用”或“丢弃预览”，只有确认后才让方案进入可执行链路。

这种设计降低了误调度风险。调度算法会影响订单状态、包裹生成、车辆和司机资源，一旦直接生效，撤销成本较高。`draft` 让调度员先查看总距离、总时间、路径明细和评分，再决定是否采用。前端还通过 `ensureNoExistingDraft()` 避免多个预览方案混淆，并在确认失败时重置预览状态。

从面试角度看，它类似业务层面的二阶段提交，但不是数据库 2PC。第一阶段产出可审查的方案，第二阶段才执行有副作用的状态变更。这对教学演示和可解释性都很重要。

#### 可能追问方向

- 多用户同时生成预览会有什么并发问题？
- 丢弃 draft 是否需要物理删除还是软删除？

### Q06：项目如何避免 API 暴露数据库内部 ID？为什么要这么做？

- 难度：初
- 核心代码：
  - `src/backend/services/route_service.py:98-115`
  - `src/backend/algorithms/route_planning.py:203-215`
  - `src/backend/core/response_schema.py:128-145`

#### 参考回答

项目内部使用自增 `id` 建外键，例如 `dispatch_id`、`vehicle_id`、`schedule_id`。但算法和服务在构造 API 响应时会转换为业务编号，例如 `route_code`、`dispatch_code`、`vehicle_code`、`package_code`。`RouteService.create_route_planning()` 明确移除内部 id，仅暴露 `_code` 业务编号。

这样做有三点收益：第一，前端和接口文档稳定，不受数据库迁移或数据重建影响；第二，避免暴露内部表结构和自增序列；第三，业务编号本身带日期或领域含义，便于演示、日志检索和面试讲解。代价是服务层需要多做一次映射，查询时也经常要从 `*_code` 找到内部 `id`。

- 如果业务编号被用户猜测，是否存在安全问题？
- 业务编号是否应该使用 UUID、雪花 ID 或日期序号？
