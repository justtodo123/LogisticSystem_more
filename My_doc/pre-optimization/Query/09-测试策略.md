### Q21：项目的测试策略应如何覆盖算法、服务和 API？

- 难度：中
- 核心代码：
  - `src/backend/tests/run_tests.py:1-260`
  - `src/backend/tests/unit/services/test_exception_service.py:1-360`
  - `src/backend/tests/unit/algorithms/test_global_schedule.py:1-260`

#### 参考回答

测试应按风险分层。算法层测试重点验证确定性、硬约束和边界条件，例如 F007 无 L1、容量不足、同订单汇聚、权重变化；F021 验证节点对分组和超重拆包；F005 验证车辆不足、部分分配和状态更新；F006 验证距离、碳排放和空任务异常。

服务层测试重点验证事务和统一响应，例如异常事件创建是否校验 target、是否标记关联实体异常、重规划失败是否回滚、版本链是否正确。API 层测试则验证认证、RBAC、参数校验和响应格式。

当前已有 `test_exception_service.py` 和算法单测，说明阶段 7 的异常服务有较完整覆盖。后续可增加端到端集成测试：初始化演示数据后跑通 F007→F021→F005→F006→异常→重规划，断言所有 `*_code`、状态流转和版本链。

### Q22：如果你是面试官，会如何用这个项目考察候选人的工程能力？

- 难度：高
- 核心代码：
  - `src/backend/main.py:82-151`
  - `src/backend/services/replan_service.py:31-219`
  - `src/backend/algorithms/global_schedule.py:103-259`
  - `src/frontend/src/components/schedule/RouteMap.vue:38-185`

#### 参考回答

可以从四个角度考察。第一是架构理解：候选人能否讲清路由、服务、算法、状态机、前端 composable 的边界。第二是业务建模：能否解释三级物流网络、订单/货物/包裹/车辆/司机/批次/路线之间的关系，以及为什么 API 暴露业务编号。第三是算法取舍：能否说明贪心、Haversine、虚拟道路和 2-opt 预留之间的现实约束。第四是工程质量：能否识别事务边界、N+1 查询、并发编号、状态机测试和 AI 降级这些隐患。

优秀回答不应只背代码，而要能指出当前 MVP 的合理性和不足。例如 ReplanService 低侵入接入重规划是阶段推进上的务实选择，但多服务各自提交会带来强一致性风险；SVG 路线图适合演示，但大规模路线可能需要 Canvas 或地图引擎；业务失败统一响应有利于前端处理，但也需要严格区分 HTTP 错误与业务错误。
