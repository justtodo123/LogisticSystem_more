# 八、性能优化

> 覆盖查询优化、缓存、分页、N+1 风险和调度复杂度。

### Q19：项目中有哪些已经实现的性能优化？还存在哪些 N+1 查询风险？

- 难度：高
- 核心代码：
  - `src/backend/algorithms/packaging.py:99-121`
  - `src/backend/services/schedule_service.py:34-94`
  - `src/backend/services/dispatch_service.py:51-94`
  - `src/backend/services/route_service.py:149-164`

#### 参考回答

已实现的优化包括：F021 打包时预加载 `goods_map` 和 `node_map`，避免按货物逐个查询节点和货物；全局调度列表使用 `_max_score_cache` 缓存历史最大 score，避免每次都全表扫描；路线列表使用分页，减少一次返回的数据量。

但项目仍存在一些 N+1 风险。例如 `DispatchService._build_dispatch_detail()` 对每个 task、每个 package、每个 goods 都单独查询；`RouteService.get_routes()` 在列表循环中再查 dispatch、batch、vehicle。MVP 数据量较小问题不明显，但如果扩大到真实物流数据，这些查询会成为瓶颈。

改进方向包括使用 SQLAlchemy `joinedload/selectinload` 预加载关系、批量收集 code 后一次性查询并构建映射、为常用筛选字段添加索引、对列表详情拆分接口避免默认展开重数据。

### Q20：如何评估 F007/F005/F006 的时间复杂度和扩展瓶颈？

- 难度：高
- 核心代码：
  - `src/backend/algorithms/global_schedule.py:186-259`
  - `src/backend/algorithms/node_dispatch.py:244-300`
  - `src/backend/algorithms/route_planning.py:157-197`

#### 参考回答

F007 主要是订单货物数乘以 L1 节点数，复杂度近似 `O(G * L1)`，其中每次还可能查询容量和节点信息。若 L1 数量和货物量增长，应该把 L1、容量、已有包裹计数预聚合到内存结构，避免循环内查询。

F005 复杂度取决于包裹数、车辆数和层级过滤。当前先按状态和方案查包裹，再按节点类型过滤；车辆匹配还会查询不同候选车辆集合。扩展后瓶颈会出现在包裹聚合、车辆选择和状态批量更新。

F006 对每个 dispatch 的 tasks 逐段计算距离，复杂度近似 `O(T)`。如果真正启用 2-opt，则可能变成 `O(N^2)` 或更高，需要限制迭代次数。

整体看，MVP 的性能目标是单次调度 10 秒内可演示，不是全局最优。规模扩大时再引入批量查询、缓存、异步任务队列和更成熟的优化算法。
