# 一、项目架构与分层设计

> 覆盖 FastAPI 分层、统一响应、RBAC 和双标识策略。

### Q01：系统为什么采用“FastAPI 路由层 + Service 编排层 + Algorithm 计算层”的分层？

- 难度：中
- 核心代码：
  - `src/backend/main.py:56-79`
  - `src/backend/services/schedule_service.py:97-180`
  - `src/backend/algorithms/global_schedule.py:103-155`

#### 参考回答

该项目的分层边界比较清晰：`main.py` 只负责创建应用、注册路由和全局中间件；API 路由负责参数接收、鉴权依赖和调用服务；Service 层负责业务事务、跨算法编排、ORM 写库和统一响应；Algorithm 层则承担确定性计算。

例如全局调度入口最终进入 `ScheduleService.create_global_schedule()`，服务层先检查活跃方案冲突，再调用 `global_schedule()` 生成计算结果，随后落库为 `GlobalSchedule` 并提交事务。算法函数本身接收 `db` 和参数，返回 `schedule_code`、`goods_schedules`、距离、时间、评分等结构化数据，不直接处理 HTTP 细节。这种方式的收益是：接口契约、业务事务、算法逻辑可独立测试；后续如果替换算法权重或接入 AI 参数，只需要通过服务层传入 `custom_weights`，无需改变路由契约。

从全局理解看，这个架构适合教学 MVP：单体部署降低运维复杂度，但内部仍保留模块边界，避免所有逻辑堆在路由函数中。它也符合项目的“双编号策略”：数据库内部使用 `id` 建关联，Service/API 返回 `*_code` 业务编号，既保证 ORM 关联效率，也避免前端暴露内部主键。

#### 可能追问方向

- Service 层返回统一响应字典与直接抛异常相比，各自优缺点是什么？

### Q02：统一响应格式在项目中如何落地？它解决了什么问题？

- 难度：初
- 核心代码：
  - `src/backend/core/response_schema.py:10-21`
  - `src/backend/main.py:82-137`

#### 参考回答

项目要求所有接口返回 `{ code, message, data, meta }`。`ResponseSchema` 和 `MetaSchema` 定义了响应结构，其中 `meta.degraded` 和 `meta.degraded_reason` 专门用于 DeepSeek 降级场景。`main.py` 中注册了 HTTP 异常和 Pydantic 校验异常处理器，把 `401/403/404/422/500` 统一转换成业务错误码和标准结构。

这样前端可以稳定地从 `response.data.data` 读取业务数据，并用 `code !== 0` 判断业务失败，而不是在每个接口里分别适配不同错误格式。对本项目特别重要的是，业务失败通常可以用 HTTP 200 + 非零 `code` 表达，例如调度约束不满足；而参数错误、认证错误仍保留对应 HTTP 状态，方便调试与网关层识别。

#### 可能追问方向

- `meta` 字段除了 AI 降级，还能承载哪些非业务数据？
- FastAPI 的 `response_model` 和手写 `dict` 响应如何权衡？

### Q03：项目如何实现 RBAC 权限边界？前后端分别承担什么职责？

- 难度：中
- 核心代码：
  - `src/backend/api/exception_events.py:31-58`
  - `src/backend/api/exception_events.py:114-119`
  - `src/frontend/src/views/Dashboard.vue:159-193`

#### 参考回答

后端通过依赖注入区分只读用户和调度员。异常列表接口使用 `get_current_user`，允许 dispatcher 和 manager 查看；创建异常、触发重规划等写操作使用 `require_dispatcher`，只有调度员能执行。前端在调度工作台中用 `authStore.isDispatcher` 控制按钮显示，manager 只能看到“只读模式”。

关键点是前端隐藏按钮只优化体验，不能作为安全边界；真正的权限判断必须在后端。关键操作采用“双层防护”：前端减少误操作，后端保证不可绕过。即使用户手动构造 HTTP 请求，后端依赖仍会返回 403 统一响应。
