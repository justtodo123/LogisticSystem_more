# P1-3 节点到货确认 - 开发文档

## 1. 业务背景与 MVP 缺陷

### 1.1 MVP 现状

MVP 中，`POST /api/simulation/deliver` 模拟送达后，自动批量激活下游包裹（`pending_pack → packed`），存在以下问题：

1. **无法标记异常**：包裹到站后若实际丢失/损坏，MVP 无入口记录
2. **级联范围过大**：批量激活该节点所有 `pending_pack` 包裹，不按货物精确匹配
3. **无审计日志**：异常原因无记录，无法追溯

### 1.2 P1-3 目标

新增「节点到货确认」功能，允许工作人员在包裹到站后逐条或批量确认正常/异常，并触发级联状态更新。

### 1.3 功能范围

| 功能 | 说明 |
| --- | --- |
| 单个确认 | `POST /api/simulation/confirm-arrival`（逐条确认） |
| 批量确认 | `POST /api/simulation/confirm-arrival-batch`（一次性确认多个包裹）|
| 查询到站包裹 | `GET /api/simulation/arrival-packages`（查询待确认包裹）|

## 2. 核心业务规则

### 2.1 F021 打包触发规则（重要变更）

| 时机 | 触发条件 | 生成包裹范围 |
| --- | --- | --- |
| 初始 F007 后 | MVP 已有 | **仅生成 L0→L1 包裹** |
| `confirm-arrival`（正常）后 | global_schedule 下存在 `pending_pack` 货物 | 生成 L1→L2 包裹（按货物实际位置）|

> **关键理解**：L1→L2 包裹不在初始 F021 中生成，而是在 `confirm-arrival`（正常）后触发 F021 才生成。

### 2.2 货物状态流转规则

| 当前状态 | 触发操作 | 下一个状态 | 说明 |
| --- | --- | --- | --- |
| `in_transit` | `deliver`（模拟送达）| `in_transit`（不变）| 仅更新 `node_id`，状态不变 |
| `in_transit` | `confirm-arrival`（正常）| 检查是否到目的地 | 若已到：`delivered`；若未到：`pending_pack` |
| `pending_pack` | F021 重新打包完成 | `packed` | 新包裹状态为 `packed` |
| `packed` | F005 调度 | `in_transit` | 货物随包裹出发 |
| `in_transit` | `confirm-arrival`（异常）| `exception` | 货物异常 |
| `exception` | — | `exception` | 不参与 F021 重新打包 |

### 2.3 订单状态流转规则

| 当前状态 | 触发条件 | 下一个状态 | 说明 |
| --- | --- | --- | --- |
| `delivering` | 任一货物 `exception` | `exception` | 订单标记异常，**但其他货物可继续流转** |
| `delivering` | 所有货物 `delivered` | `completed` | 订单完成 |
| `exception` | — | `exception` | 仅标记，不阻止其他货物流转 |

### 2.4 包裹状态流转规则

| 当前状态 | 触发操作 | 下一个状态 | 说明 |
| --- | --- | --- | --- |
| `in_transit` | `deliver`（模拟送达）| `delivered` | 包裹到站 |
| `delivered` | `confirm-arrival`（正常）| `delivered`（不变）| 无需变更 |
| `delivered` | `confirm-arrival`（异常）| `exception` | 包裹异常，级联下游包裹 |
| `packed` | F021 生成 | `packed` | 新包裹状态 |
| `pending_pack` | — | `pending_pack` | 等待 `confirm-arrival` 激活 |

### 2.5 F021 重新打包规则

当 `confirm-arrival`（正常）后，若货物未到目的地，触发 F021 重新打包：

1. 遍历 `global_schedule.goods_schedules`
2. 对每条 `goods_schedule`：
   - 若 `goods.status == pending_pack`：
     - `from_node = goods.node_id`（当前所在节点）
     - `to_node = path[index(goods.node_id) + 1]`（按实际位置取 path 下一个节点）
     - 生成新的下游包裹（`packed`）
   - 更新 `goods.status = packed`（F021 完成后）
3. 若 `goods.status == exception`：**跳过**，不参与重新打包

## 3. 完整状态转换链条

### 3.1 场景设定

- 订单 O_1 含货物 g_1，路径：`SC001（L0）→ SO001（L1）→ SO027（L2/目的地）`
- 订单 O_2 含货物 g_2，路径：`SC001（L0）→ SO001（L1）→ SO027（L2/目的地）`
- 包裹 C（L0→L1）含 g_1，包裹 D（L0→L1）含 g_2
- 包裹 E'（L1→L2）含 g_1，包裹 F（L1→L2）含 g_2（异常后不生成）

### 3.2 步骤详解

#### 步骤 1：F007 + F021（初始打包）

| 实体 | 状态变更 | 说明 |
| --- | --- | --- |
| g_1、g_2 | `pending_pack` → `packed` | F021 打包完成 |
| C（L0→L1） | `pending_pack` → `packed` | **生成**（含 g_1）|
| D（L0→L1） | `pending_pack` → `packed` | **生成**（含 g_2）|
| E、F | **不生成** | L1→L2 包裹在 confirm-arrival 后才生成 |
| O_1、O_2 | `pending` → `delivering` | 调度完成 |

---

#### 步骤 2：F005（L0→L1 调度）

| 实体 | 状态变更 | 说明 |
| --- | --- | --- |
| C、D | `packed` → `in_transit` | 车辆出发 |
| g_1、g_2 | `packed` → `in_transit` | 货物在途 |

---

#### 步骤 3：模拟送达 `deliver`（L0→L1 到站）← **改造点 1**

> **改造**：`goods.status` **保持 `in_transit`**（不改为 `pending_pack`）
> 仅更新 `goods.node_id = to_node_id`（记录货物实际到达节点）

| 实体 | 状态变更 | 说明 |
| --- | --- | --- |
| C | `in_transit` → `delivered` | 包裹到站 |
| D | `in_transit` → `delivered` | 包裹到站 |
| g_1 | `in_transit`（不变）| node_id 更新为 L1 |
| g_2 | `in_transit`（不变）| node_id 更新为 L1 |

> ⚠️ **E、F 不存在**（初始未生成，无需激活）

---

#### 步骤 4：confirm-arrival（节点到货确认）← **本 P1 核心**

##### 正常路径（C）：

| 实体 | 状态变更 | 说明 |
| --- | --- | --- |
| C | `delivered`（已是）| 无需变更 |
| g_1 | `in_transit` → 检查是否到目的地 | 货物到站 |
| | 若已到目的地：`delivered` | 无需重新打包 |
| | 若未到目的地：`pending_pack` | 等待重新打包 |
| | | **触发 F021**：global_schedule 下存在 `pending_pack` 货物 |
| E'（新包裹） | `packed` | **F021 生成**，含 g_1 |
| | | from_node = g_1.node_id（L1）|
| | | to_node = path[index(L1) + 1]（下一个节点）|
| g_1 | `pending_pack` → `packed` | F021 完成后 |
| O_1 | `delivering`（不变）| 正常流转 |

---

##### 异常路径（D）：

| 实体 | 状态变更 | 说明 |
| --- | --- | --- |
| D | `delivered` → `exception` | 包裹异常 |
| g_2 | `in_transit` → `exception` | 货物异常 |
| O_2 | `delivering` → `exception` | 订单标记异常（其他货物可继续流转）|
| F（下游包裹）| **不存在** | 无需级联 |

> **不触发 F021**（g_2 已为 `exception`，不参与重新打包）

---

#### 步骤 5：F005（L1→L2 调度）

| 实体 | 状态变更 | 说明 |
| --- | --- | --- |
| E' | `packed` → `in_transit` | 新包裹被调度 |
| g_1 | `packed` → `in_transit` | 货物随包裹出发 |

> ⚠️ D 状态为 `exception`，不会被 F005 选中

---

#### 步骤 6：模拟送达 `deliver`（L1→L2 到站）

| 实体 | 状态变更 | 说明 |
| --- | --- | --- |
| E' | `in_transit` → `delivered` | 包裹到站 |
| g_1 | `in_transit`（不变）| node_id 更新为 L2/目的地 |

---

#### 步骤 7：confirm-arrival（L1→L2 到货确认）

##### 场景：E'=正常

| 实体 | 状态变更 | 说明 |
| --- | --- | --- |
| E' | `delivered`（已是）| 无需变更 |
| g_1 | `in_transit` → 检查是否到目的地 | 货物到站 |
| | 已到目的地：`delivered` | 无需重新打包 |
| | 未到目的地：`pending_pack` | 等待重新打包（但此处已到，不会发生）|
| O_1 | `delivering` → `completed` | 所有货物已送达 |

## 6. 实现伪代码要点

### 6.1 `confirm_arrival` 核心逻辑（单个确认）

```python
def confirm_arrival(db, schedule_code, package_code, is_normal, exception_subtype, remark):
    # 1. 查询包裹
    package = db.query(Package).filter_by(package_code=package_code).one()
    
    # 2. 正常路径
    if is_normal:
        # 2.1 更新包裹状态
        package.status = "delivered"
        
        # 2.2 处理货物：检查是否到目的地
        for goods_item in package.goods_items:
            goods = db.query(Goods).filter_by(goods_code=goods_item["goods_code"]).one()
            
            # 检查是否到目的地
            order = db.query(Order).filter_by(order_code=goods_item["order_code"]).one()
            if goods.node_id == order.destination_node_id:
                goods.status = "delivered"
            else:
                goods.status = "pending_pack"
                
                # 2.3 触发 F021 重新打包
                trigger_repacking(db, schedule_code)
        
        # 2.4 检查订单是否完成
        check_order_completion(db, order.order_code)
        
    # 3. 异常路径
    else:
        # 3.1 更新包裹状态
        package.status = "exception"
        
        # 3.2 处理货物
        for goods_item in package.goods_items:
            goods = db.query(Goods).filter_by(goods_code=goods_item["goods_code"]).one()
            goods.status = "exception"
            
            # 3.3 写入 exception_events（审计用，不触发 replan）
            create_exception_event(
                db, 
                schedule_code=schedule_code,
                package_code=package_code,
                goods_code=goods_item["goods_code"],
                exception_type="package",
                exception_subtype=exception_subtype,
                remark=remark
            )
        
        # 3.4 更新订单状态
        order = db.query(Order).filter_by(order_code=goods_item["order_code"]).one()
        order.status = "exception"
        
        # 3.5 级联下游包裹（若存在）
        cascade_exception_packages(db, schedule_code, package_code)
    
    # 注意：单个确认不在此处 commit，由调用方（批量确认）控制事务
    # db.commit()
    
    return {
        "package_code": package_code,
        "status": package.status,
        "goods_status": goods.status if is_normal else "exception",
        "order_status": order.status if not is_normal else None
    }
```

### 6.2 `confirm_arrival_batch` 核心逻辑（批量确认）

```python
def confirm_arrival_batch(db, schedule_code, confirmations):
    # 1. 预校验所有包裹（事务性：任一失败则全部回滚）
    for conf in confirmations:
        package = db.query(Package).filter_by(package_code=conf["package_code"]).first()
        
        # 1.1 包裹不存在
        if not package:
            raise HTTPException(400, f"包裹 {conf['package_code']} 不存在")
        
        # 1.2 包裹不属于该 schedule
        if package.schedule.schedule_code != schedule_code:
            raise HTTPException(400, f"包裹 {conf['package_code']} 不属于该调度方案")
        
        # 1.3 包裹状态不正确（必须是 in_transit 或 delivered）
        if package.status not in ["in_transit", "delivered"]:
            raise HTTPException(400, f"包裹 {conf['package_code']} 状态不正确：{package.status}")
    
    # 2. 批量确认（事务性）
    results = []
    try:
        for conf in confirmations:
            # 2.1 复用单个确认逻辑
            result = confirm_arrival(
                db,
                schedule_code=schedule_code,
                package_code=conf["package_code"],
                is_normal=conf["is_normal"],
                exception_subtype=conf.get("exception_subtype"),
                remark=conf.get("remark")
            )
            results.append(result)
        
        db.commit()
        
        # 3. 返回成功响应
        return {
            "total": len(confirmations),
            "success_count": len(results),
            "failed_count": 0,
            "results": results
        }
        
    except Exception as e:
        db.rollback()
        # 4. 返回失败响应（已回滚）
        raise HTTPException(400, f"批量确认失败，已回滚：{str(e)}")
```

### 6.2 `trigger_repacking` 伪代码

```python
def trigger_repacking(db, schedule_code):
    # 1. 查询 global_schedule
    schedule = db.query(GlobalSchedule).filter_by(schedule_code=schedule_code).one()
    goods_schedules = schedule.goods_schedules  # JSON
    
    # 2. 遍历 goods_schedules
    for gs in goods_schedules:
        goods = db.query(Goods).filter_by(goods_code=gs["goods_code"]).one()
        
        # 3. 仅处理 pending_pack 货物
        if goods.status == "pending_pack":
            # 3.1 确定 from_node 和 to_node
            from_node = goods.node_id
            path = gs["path"]
            current_index = path.index(from_node)
            to_node = path[current_index + 1]  # 下一个节点
            
            # 3.2 检查是否已存在相同 from_node → to_node 的包裹
            existing_package = db.query(Package).filter_by(
                schedule_id=schedule.id,
                from_node_id=from_node,
                to_node_id=to_node,
                status="pending_pack"
            ).first()
            
            if not existing_package:
                # 3.3 生成新包裹
                new_package = Package(
                    package_code=generate_package_code(),
                    schedule_id=schedule.id,
                    from_node_id=from_node,
                    to_node_id=to_node,
                    status="packed",  # ← 关键：新包裹状态为 packed
                    goods_items=[{"goods_code": gs["goods_code"], "order_code": gs["order_code"]}]
                )
                db.add(new_package)
            
            # 3.4 更新货物状态
            goods.status = "packed"
```

```python
            # ⚠️ 移除：goods.status = "packed"  # 不直接改为 packed
            # ⚠️ 移除：批量激活下游包裹的逻辑
    
    db.commit()
```

## 8. 关键约束与非功能需求

1. **F021 重新打包必须是确定性的**：同输入可复现，不使用随机种子
2. **`confirm-arrival` 必须幂等**：重复提交相同 `package_code` 应返回错误
3. **异常必须写入 `exception_events`**：审计用，但不自动触发 replan
4. **F005 无需改造**：算法层已过滤 `exception` 包裹
5. **`deliver` 必须处理 `exception` 包裹**：入口处加校验，若包裹 `status=exception`，静默跳过

## 9. 附录：与 MVP 的差异对比

| 维度 | MVP | P1-3 |
| --- | --- | --- |
| F021 打包时机 | 初始 F007 后生成所有包裹 | 初始仅生成 L0→L1，L1→L2 在 confirm-arrival 后生成 |
| `deliver` 后货物状态 | `in_transit → packed` | `in_transit`（不变），仅更新 `node_id` |

| 审计日志 | 无 | 写入 `exception_events` |
| 订单异常语义 | 订单下所有货物停止 | 订单标记异常，但其他货物可继续流转 |

### 10.4 关键经验

1. **fixture 数据复用**：测试应优先使用 `conftest.py` 中的 fixture 数据，避免 UNIQUE 约束冲突
2. **autoflush=False**：`sessionmaker(autocommit=False, autoflush=False)` 配置下，服务层状态更新后需要显式调用 `db_session.flush()` 才能确保 `refresh()` 读到最新数据
3. **Git 辅助文件**：`out-test-arrival-confirm.md` 是测试日志输出文件，不纳入版本控制
3. **更新 API 契约**：如果 API 有变化，更新 `docs/api-contract/api-contract-p1-3.md`
