### 3.3 服务层设计

#### 3.3.1 ExceptionService

**文件**：`src/backend/services/exception_service.py`

**核心方法**：

| 方法 | 说明 |
|------|------|
| `create_exception_event()` | 创建异常事件，自动标记关联实体状态 → exception |
| `get_exception_events()` | 异常列表（分页 + 按 status / exception_type 筛选） |
| `get_exception_event_by_code()` | 异常详情 |
| `update_exception()` | 更新异常（支持 status 变更，自动记录 resolved_at） |
| `resolve_exception()` | 标记已解决（重复标记拒绝） |
| `trigger_replan()` | 触发重规划，根据 action 调用 ReplanService |

**创建异常时的自动状态变更**：

```
① 查询 related_schedule_code → GlobalSchedule
② 遍历 schedule.order_codes → 订单 delivering → exception
   同时遍历 order.goods → 货物 packed/in_transit → exception
③ 查询 schedule_id 关联的包裹 → packed/in_transit/pending_pack → exception
④ 若 target_type=vehicle：
   - 车辆 → disabled
   - 查询 vehicle.id 关联的 NodeDispatch → dispatch_id 列表
   - 按 dispatch_id 批量更新包裹 → exception
   - 从包裹 goods_items 提取 goods_code 批量更新货物 → exception
```

#### 3.3.2 ReplanService（方案A核心）

**文件**：`src/backend/services/replan_service.py`

**核心方法**：

```python
@staticmethod
async def redispatch(db, original_schedule_code, replan_reason, event=None):
    """重调度（F007→F021→F005→F006）"""
    ① 查询原 GlobalSchedule
    ② 提取 order_codes + algorithm_type
    ③ 从 event 提取 excluded_nodes / excluded_vehicles
    ④ 调用 ScheduleService.create_global_schedule(
           order_codes, algorithm, db,
           excluded_nodes=..., is_replan=True  # 仅调度 exception 订单
       )
    ⑤ 更新新版 GlobalSchedule 版本链（version+1, parent_id, is_replan, replan_reason）
    ⑥ 调用 DispatchService.create_node_dispatch(
           schedule_code=new_schedule_code, demo_mode=False, db,
           excluded_vehicles=..., is_replan=True  # 仅调度 exception 包裹
       )
       → F006 自动触发
    ⑦ 返回 { schedule_code, batch_code, version, is_replan, ... }

@staticmethod
async def reroute(db, original_route_code, replan_reason, excluded_vehicles=None):
    """重路径规划（F006）"""
    ① 查询原 Route
    ② Route.dispatch_id → NodeDispatch → DispatchBatch
    ③ 提取 dispatch_codes（仅当前 dispatch）
    ④ 调用 RouteService.create_route_planning(
           batch_code, dispatch_codes, db,
           excluded_vehicles=...
       )
    ⑤ 更新新版 Route 版本链（version+1, parent_id, is_replan, replan_reason）
    ⑥ 返回 { batch_code, route_codes, version, is_replan, ... }
```

**关键差异（与计划文档对比）**：
- ✅ 方法改为 `async`（因 ScheduleService/DispatchService/RouteService 均为 async）
- ✅ `redispatch` 接收 `event` 参数提取排除信息
- ✅ `reroute` 接收 `excluded_vehicles` 参数
- ✅ 内部通过延迟导入避免循环依赖

### 4.1 Redispatch 前置条件

| 条件 | 说明 |
|------|------|
| **全局调度已完成** | 必须存在 `related_schedule_code` 对应的 `GlobalSchedule` 记录 |
| 节点调度 **不要求** 完成 | `ReplanService.redispatch()` 内部自行调用 `DispatchService` 执行 F005+F006 |

> **关键设计**：`redispatch` 只需完成阶段3即可使用。创建异常事件仅将关联实体标记为 `exception`，作为重调度时的筛选条件。

### 4.2 Reroute 前置条件

| 条件 | 说明 |
|------|------|
| **节点调度已完成** | `target_code` 必须指向已存在的 `Route` 记录（F005 完成后自动触发 F006 生成） |
| 目标路线存在 | 可通过 `GET /api/routes` 确认 |

> **关键设计**：`reroute` 需要完成阶段4。它操作的是 F006 生成的 `Route` 记录，不重新调度，不修改实体状态。

## 七、设计决策

### 7.1 方案A — 不修改现有服务层

- `ReplanService` 调用 `ScheduleService`、`DispatchService`、`RouteService`
- 版本链逻辑集中在 `ReplanService`，原服务层代码零修改
- 符合开闭原则，确保回归安全

### 7.2 重规划仅调度 exception 状态实体

- `is_replan=True` 传入各服务层，仅对 `exception` 状态的订单/包裹调度
- 正常配送中的实体不受影响

### 7.3 reroute 不修改状态

- 与 redispatch 不同，reroute 不重置订单/货物/包裹为 exception
- 仅生成新路线记录，原路线保留用于对比

### 7.4 创建异常自动关联

- 创建异常时自动将关联实体状态标记为 `exception`
- 车辆异常特殊处理：车辆 → `disabled` + 批量更新关联包裹和货物

### 7.5 repack_at_l1 精确匹配修复

- 修复 `.first()` 改为 `.all()` + `order_code` 精确匹配
- 解决多订单同路线场景下包裹错误复用导致遗漏的 BUG

### 7.6 Redispatch 只需全局调度完成

- 前置条件仅为阶段3（`schedule_code` 存在）
- `ReplanService.redispatch()` 内部自行调用 `DispatchService`，不需要预先执行节点间调度

### 7.7 Reroute 需节点调度完成

- 前置条件为阶段4（`Route` 记录存在）
- 因为操作对象是 F006 生成的 Route 记录
