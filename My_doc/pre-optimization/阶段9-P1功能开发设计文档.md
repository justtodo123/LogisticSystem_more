# 阶段9 - P1功能开发设计文档

## 1. 引言

### 1.1 背景

当前系统中，P1功能（F015方案解释、F016方案审查、F017异常分析）的API端点返回501占位响应。本阶段目标是实现这三个功能，将其改为实际可用的功能。

### 1.2 目标

1. 实现F015方案解释功能：为调度方案生成自然语言解释
2. 实现F016方案审查功能：识别调度方案的潜在风险
3. 实现F017异常分析功能：分析异常原因并给出调整建议
4. 确保错误处理和降级策略正确实现

### 1.3 范围

本阶段仅实现后端功能，前端交互（侧边栏显示）由前端团队实现。后端提供完整的API接口，包括数据查询、DeepSeek API调用、响应返回。

## 2. 总体设计

### 2.1 系统架构

```
前端调度工作台
    ↓ (点击按钮)
POST /api/ai/explain (或 /review, /analyze-exception)
    ↓
FastAPI路由层 (api/ai.py)
    ↓
服务层 (services/deepseek_service.py)
    ↓
DeepSeek API (异步调用)
    ↓
返回统一响应格式
```

### 2.2 模块划分

| 模块 | 文件路径 | 职责 |
| --- | --- | --- |
| API路由层 | `src/backend/api/ai.py` | 接收请求、参数校验、调用服务层、返回响应 |
| DeepSeek服务层 | `src/backend/services/deepseek_service.py` | 构建提示词、调用DeepSeek API、解析响应 |
| 数据查询服务层 | `src/backend/services/schedule_service.py`, `dispatch_service.py`, `exception_service.py` | 查询调度方案、批次、异常事件数据 |
| Pydantic模型 | `src/backend/schemas/ai.py` | 请求/响应数据验证 |

## 3. 详细设计

### 3.1 F015 - 方案解释功能

#### 3.1.1 API接口定义

**端点**: `POST /api/ai/explain`

**请求体**:
```json
{
  "schedule_code": "GS20260609001",  // 可选，调度方案编码
  "batch_code": "DB20260609001"       // 可选，调度批次编码
}
```

**约束**: `schedule_code`和`batch_code`至少一个必须提供。

**响应体** (成功):
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "explanation": "该调度方案优先选择了距离最短的路径...",
    "key_decisions": [
      "选择SC001作为L0存储中心",
      "使用2辆货车进行L0→L1运输"
    ],
    "potential_risks": [
      "L1分拣中心容量接近上限",
      "部分路线距离较长，可能增加配送时间"
    ]
  },
  "meta": {
    "degraded": false,
    "degraded_reason": null
  }
}
```

**响应体** (降级):
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "explanation": "AI服务暂时不可用，请稍后重试",
    "key_decisions": [],
    "potential_risks": []
  },
  "meta": {
    "degraded": true,
    "degraded_reason": "DeepSeek API调用超时"
  }
}
```

**错误码**:
- `40001`: 输入参数错误（如`schedule_code`和`batch_code`都为空）
- `40401`: 资源不存在（如`schedule_code`对应的调度方案不存在）
- `50100`: DeepSeek API调用失败（降级提示）

#### 3.1.2 数据查询逻辑

**输入处理**:
1. 如果提供了`schedule_code` → 调用`ScheduleService.get_global_schedule(schedule_code)`查询调度方案详情
2. 如果提供了`batch_code` → 调用`DispatchService.get_dispatch_batch_detail(batch_code)`查询批次详情
3. 如果两个都提供 → 查询两个数据，优先使用调度方案数据

**查询的数据字段**:

从`global_schedules`表查询:
- `schedule_code`: 调度方案编码
- `total_distance`: 总距离
- `total_time`: 总时间
- `total_goods`: 总货物数
- `score`: 评分
- `algorithm_type`: 算法类型
- `goods_schedules`: 货物调度路径 (JSON)
- `created_at`: 创建时间

从关联的`packages`表查询:
- `package_code`: 包裹编码
- `status`: 状态
- `goods_items`: 货物项 (JSON)

**数据组装**:
将查询的数据组装成字典，传递给`DeepSeekService.explain_schedule`方法。

#### 3.1.3 DeepSeek提示词模板

**系统提示词**:
```

输出格式要求（严格JSON格式）：
{
  "explanation": "字符串，整体解释文本",
  "key_decisions": ["字符串数组，关键决策列表"],
  "potential_risks": ["字符串数组，潜在风险列表"],

注意：
1. 解释应该清晰易懂，避免使用过于专业的术语
2. 关键决策应该具体、可操作
3. 潜在风险应该实际、可预防
```

**用户提示词模板**:
```

```


#### 3.1.4 服务层方法设计

**方法签名**:
```python
@staticmethod
async def explain_schedule(
    schedule_data: Dict[str, Any], 
    batch_data: Optional[Dict[str, Any]] = None
) -> Dict[str, Any]:
    """
    生成调度方案解释
    
    Args:
        schedule_data: 调度方案数据字典
        batch_data: 批次数据字典（可选）
    
    Returns:
        包含explanation、key_decisions、potential_risks的字典
    """
```

**实现逻辑**:
1. 构建系统提示词和用户提示词
2. 调用DeepSeek API（使用现有的`_build_request_body`、`_build_api_url`、`_extract_response_content`方法）
3. 解析响应内容（期望JSON格式）
4. 如果解析失败，返回默认解释 + `degraded=true`
5. 返回解析结果

**错误处理**:
- DeepSeek API调用超时（30秒）→ 返回默认解释 + `meta.degraded=true`
- DeepSeek API返回错误（HTTP状态码非200）→ 同上
- 响应格式解析失败（JSON解析错误）→ 同上

```
注意：
1. 风险类型应该与阶段7的异常类型保持一致

3. 严重级别应该根据实际数据计算（如超载百分比、超时时间）
```

#### 3.3.3 DeepSeek提示词模板

**系统提示词**:
```
你是一个物流异常处理专家，擅长分析异常原因并给出调整建议。请根据提供的异常事件数据，分析根本原因，并给出具体、可操作的处理建议。

输出格式要求（严格JSON格式）：
{
  "root_cause": "字符串，根本原因（简明扼要）",
  "suggestions": [
    "字符串，建议1（具体、可操作，如'建议将包裹C重新分配给车辆D，因为...'）",
    "字符串，建议2"
  ],

}

分析原则：
1. 根本原因应该准确、有依据（基于异常类型、子类型、目标类型）
2. 建议应该具体、可操作（避免"建议优化路线"这种模糊建议，应该给出具体方案）
3. 建议应该参考PRD中的示例格式（如"建议将包裹C重新分配给车辆D，因为..."）
4. auto_fix_available应该根据实际情况判断：
   - 如果推荐操作是`reroute`（重路径规划），通常可以自动修复（auto_fix_available=true）
   - 如果推荐操作是`redispatch`（重调度），通常需要人工确认（auto_fix_available=false）
   - 如果异常类型是`node`（节点异常），通常需要人工确认（auto_fix_available=false）

示例建议格式：
- 道路异常："建议将包裹C重新分配给车辆D，因为车辆D当前路线不经过异常道路"
- 包裹异常："建议将损坏的包裹C重新打包，使用新的包裹编码PKG999"
- 节点异常："建议将L1分拣中心从SC001更换为SC002，因为SC001容量不足"
```

### 3.4 错误处理和降级策略

本节定义三个功能（F015/F016/F017）的错误处理和降级策略，确保系统在DeepSeek API不可用或返回错误时仍能提供基本功能。

#### 3.4.1 错误码设计

参考现有错误处理模式（如`ai.py`中的`50100`），设计以下错误码：

| 错误码 | 含义 | 使用场景 |
| --- | --- | --- |
| `40001` | 输入参数错误 | `schedule_code`和`batch_code`都为空；`event_code`为空 |
| `40401` | 资源不存在 | `schedule_code`对应的调度方案不存在；`event_code`对应的异常事件不存在 |
| `50100` | DeepSeek API调用失败（降级提示） | DeepSeek API超时、返回错误、响应格式解析失败 |
| `50101` | DeepSeek API调用超时 |  specifically for timeout errors (optional, can use 50100 with degraded_reason) |
| `50102` | DeepSeek响应格式错误 | 响应不是有效JSON，或缺少必需字段 |

**注意**：错误码`50101`和`50102`是可选的，也可以统一使用`50100`，通过`meta.degraded_reason`区分具体错误类型。

#### 3.4.2 降级策略

当DeepSeek API调用失败时，系统应该返回降级响应，而不是返回错误码。降级响应的特点是：
- HTTP状态码：200（不是500）
- `code`：0（业务成功）
- `data`：包含默认值的响应
- `meta.degraded`：true
- `meta.degraded_reason`：具体错误原因

**F015降级响应示例**：
```json
{
  "code": 0,
  "message": "success",
```

#### 3.4.3 错误处理流程

以下是三个功能的统一错误处理流程：

```
开始
  ↓
调用DeepSeek API
  ↓
成功？
  ↓ Yes
解析响应（JSON）
  ↓
解析成功？
  ↓ Yes
返回解析结果
  ↓
No (解析失败)
  ↓
记录错误日志
  ↓
返回降级响应（meta.degraded=true, meta.degraded_reason="DeepSeek响应格式错误"）
  ↓
No (API调用失败)
  ↓
记录错误日志（包含HTTP状态码、错误信息）
  ↓
返回降级响应（meta.degraded=true, meta.degraded_reason="DeepSeek API调用超时/返回错误"）
```

#### 3.4.4 日志记录建议

为了便于调试和监控，建议在以下位置记录日志：

1. **API调用前**：记录请求参数（不包含敏感信息）
   ```python
   logger.info(f"Calling DeepSeek API for F015 explain_schedule, schedule_code={schedule_code}")
   ```

2. **API调用失败时**：记录错误详情（HTTP状态码、错误信息）
   ```python
   logger.error(f"DeepSeek API call failed: status_code={response.status_code}, error={error_msg}")
   ```

3. **响应解析失败时**：记录原始响应内容（可能包含敏感信息，需脱敏）
   ```python
   logger.error(f"Failed to parse DeepSeek response: {content[:100]}...")  # 只记录前100字符
   ```

4. **返回降级响应时**：记录降级原因
   ```python
   logger.warning(f"Returning degraded response: degraded_reason={degraded_reason}")
   ```

#### 3.4.5 重试机制（可选）

当前设计不包含重试机制（为了简化实现）。但如果需要提高可靠性，可以考虑添加：
- **重试次数**：1次（避免增加响应时间）
- **重试间隔**：1秒
- **重试条件**：仅限网络错误（如timeout），不包括HTTP 4xx错误

**注意**：重试机制会增加响应时间，需要权衡可靠性和用户体验。

```python
@router.post("/ai/explain", response_model=AiExplainResponse)
async def explain_schedule(request: AiExplainRequest, db: Session = Depends(get_db)):
    """F015 方案解释"""
    try:
        # 1. 参数校验
        if not request.schedule_code and not request.batch_code:
            raise BadRequestException("schedule_code和batch_code至少一个必须提供")
            
        # 2. 查询数据
        schedule_data = None
        batch_data = None
        
        if request.schedule_code:
            schedule = ScheduleService.get_global_schedule(db, request.schedule_code)
            if not schedule:
                raise NotFoundException(f"调度方案不存在: {request.schedule_code}")
            schedule_data = {
                "schedule_code": schedule.schedule_code,
                "total_distance": schedule.total_distance,
                # ... 其他字段
            }
            
        if request.batch_code:
            batch = DispatchService.get_dispatch_batch_detail(db, request.batch_code)
            if not batch:
                raise NotFoundException(f"调度批次不存在: {request.batch_code}")
            batch_data = {
                "batch_code": batch.batch_code,
                # ... 其他字段
            }
            
        # 3. 调用DeepSeek服务
        result = await DeepSeekService.explain_schedule(schedule_data, batch_data)
        
        # 4. 返回响应
        return {
            "code": 0,
            "message": "success",
            "data": result,
            "meta": {"degraded": False, "degraded_reason": None}
        }
        
    except BadRequestException as e:
        return {"code": 40001, "message": str(e), "data": None, "meta": {}}
    except NotFoundException as e:
        return {"code": 40401, "message": str(e), "data": None, "meta": {}}
    except Exception as e:
        logger.error(f"Failed to explain schedule: {e}")
        return {
            "code": 0,

            "data": {
                "explanation": "AI服务暂时不可用，请稍后重试",
```

## 6. 风险评估

### 6.1 技术风险

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| DeepSeek API调用超时 | 用户体验差 | 设置合理超时时间（30秒），实现降级策略 |
| DeepSeek API返回格式错误 | 功能不可用 | 严格验证响应格式，解析失败时返回默认结果 |
| 数据查询性能差 | 响应时间长 | 优化SQL查询，添加索引 |
| 提示词设计不合理 | AI生成质量差 | 多次迭代优化提示词，参考实际测试结果 |

### 6.2 进度风险

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| DeepSeek API调用失败 | 无法测试 | 使用Mock进行测试，确保业务逻辑正确 |
| 前端联调延迟 | 无法及时验证 | 先完成后端开发和单元测试，前端联调放在最后 |
