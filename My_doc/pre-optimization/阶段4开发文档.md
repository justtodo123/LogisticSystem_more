# 阶段4开发文档：节点间调度（F005）

## 1. 开发目标

完成F005节点间调度功能，实现：
- 创建 `dispatch_batches` 和 `node_dispatches` 表
- 实现F005算法（两次串行调用：L0→L1 和 L1→L2）
- 实现 `POST /api/schedule/node-dispatch` 接口
- 支持 `demo_mode` 参数控制调度模式：
  - `demo_mode=true`（演示模式）：一次API调用自动完成两次调度（L0→L1 + L1→L2），包括自动模拟送达、自动重新打包
  - `demo_mode=false`（生产模式）：需要用户手动触发各步骤（首次调用L0→L1 → 手动模拟送达 → 手动重新打包 → 第二次调用L1→L2）
- 自动检测调用阶段（通过检查是否已有 `l0_l1_done` 状态的批次）

**两种模式的行为差异**：
1. **demo_mode=true**：
   - 用户调用一次 `POST /api/schedule/node-dispatch (demo_mode=true)`
   - 系统自动完成：L0→L1调度 → 模拟L0→L1送达 → L1重新打包 → L1→L2调度 → 模拟L1→L2送达
   - 所有步骤自动完成，适用于课堂演示

2. **demo_mode=false**：
   - 用户调用 `POST /api/schedule/node-dispatch (demo_mode=false)`（首次调用，L0→L1）
   - 用户手动调用 `POST /api/simulation/deliver`（模拟L0→L1送达）
   - 用户手动调用 `POST /api/packages/{package_code}/repack`（L1重新打包）
   - 用户调用 `POST /api/schedule/node-dispatch (demo_mode=false)`（第二次调用，L1→L2）
   - 用户手动调用 `POST /api/simulation/deliver`（模拟L1→L2送达）
   - 所有步骤需要用户手动触发，适用于真实流程

**重要说明**：`demo_mode=false` 的完整流程（包括L1送达后自动重新打包、自动执行第二次F005）在**阶段6**实现，详见《阶段6-模拟送达-开发文档.md》。

## 2. 数据库设计

### 2.1 新增表结构

#### dispatch_batches（调度批次表）
```sql
CREATE TABLE dispatch_batches (
    id BIGINT PRIMARY KEY AUTOINCREMENT,
    batch_code VARCHAR(64) UNIQUE NOT NULL,
    global_schedule_id BIGINT NOT NULL REFERENCES global_schedules(id),
    status VARCHAR(32) NOT NULL DEFAULT 'pending',
    demo_mode BOOLEAN NOT NULL DEFAULT FALSE,  -- 演示模式标识
    l0_l1_dispatch_count INT NOT NULL DEFAULT 0,  -- L0→L1调度次数
    l1_l2_dispatch_count INT NOT NULL DEFAULT 0,  -- L1→L2调度次数
    algorithm_type VARCHAR(32) NOT NULL DEFAULT 'traditional',  -- 算法类型（与架构设计一致）
    version INT NOT NULL DEFAULT 1,  -- 版本号
    parent_id BIGINT NULL REFERENCES dispatch_batches(id),  -- 父版本（重规划用）
    replan_reason VARCHAR(500) NULL,  -- 重规划原因（与架构设计一致，长度500）
    is_replan BOOLEAN NOT NULL DEFAULT FALSE,  -- 是否重规划
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

#### node_dispatches（节点调度明细表）
```sql
CREATE TABLE node_dispatches (
    id BIGINT PRIMARY KEY AUTOINCREMENT,
    dispatch_code VARCHAR(64) UNIQUE NOT NULL,
    dispatch_batch_id BIGINT NOT NULL REFERENCES dispatch_batches(id),
    level_phase TINYINT NOT NULL,  -- 0: L0→L1, 1: L1→L2
    vehicle_id BIGINT NOT NULL REFERENCES vehicles(id),
    driver_id BIGINT NULL REFERENCES drivers(id),  -- 可为NULL（车辆可能无司机）
    tasks JSON NOT NULL,  -- [{"from_node_code":"SC001","to_node_code":"L1001","package_codes":["PKG001"],"is_return":false}]
    total_distance DECIMAL(12,3) NOT NULL,  -- 任务总成本（距离，与架构设计一致）
    total_time DECIMAL(12,3) NOT NULL,  -- 任务总成本（时间，与架构设计一致）
    algorithm_type VARCHAR(32) NOT NULL DEFAULT 'traditional',  -- 算法类型（与架构设计一致）
    version INT NOT NULL DEFAULT 1,  -- 版本号
    parent_id BIGINT NULL REFERENCES node_dispatches(id),  -- 父版本（重规划用）
    replan_reason VARCHAR(500) NULL,  -- 重规划原因（与架构设计一致，长度500）
    is_replan BOOLEAN NOT NULL DEFAULT FALSE,  -- 是否重规划
    assigned_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,  -- 分配时间（与架构设计一致）
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

## 3. F005算法设计

### 3.1 算法输入

- `schedule_code`：全局调度方案编码
- `demo_mode`：是否演示模式（bool）

**说明**：API只调用一次，后端自动执行单次F005，检测包裹层级（如果混合层级则报错，否则执行对应层级的节点调度）。`target_level`是算法内部变量，不是输入参数。

### 3.2 算法输出

**输出格式**（PRD要求，API层暴露*_code而非数据库ID）：
```json
[
  {
    "vehicle_code": "VEHSC00101",
    "driver_code": "DRVSC00101",
    "tasks": [
      {
        "from_node_code": "SC001",
        "to_node_code": "L1001",
        "package_codes": ["PKG001", "PKG002"],
        "is_return": false
      },
      {
        "from_node_code": "L1001",
        "to_node_code": "L1001",
        "package_codes": [],
        "is_return": true
      }
    ],
    "total_distance": 15.2,
    "total_time": 45.5
  }
]
```

**说明**：
- 输出为数组，每个元素代表一辆车的调度方案
- **重要**：API层统一暴露 `*_code` 业务编号（如 `vehicle_code`、`driver_code`），绝不暴露数据库 `id`（项目宪章第3条）
- `tasks` 包含运输任务和返回任务（`is_return=true`）
- `total_distance` 和 `total_time` 为该车任务总成本

### 3.3 算法流程

#### 车辆匹配策略（距离评分逻辑简化）

**背景**：PRD要求"按距离评分（距离起始节点近的空闲车辆优先）"，但现有数据库不支持查看车辆实时地址（`vehicles`表无`current_location`字段）。

**简化策略**（阶段4采用）：
1. **载重匹配**：优先选择载重足够的车辆（`capacity` >= 包裹总重量，按 `capacity` 升序，避免大车小用）
2. **节点优先级**：
   - 第一优先：本节点空闲车辆（`node_id=当前节点` AND `status='idle'`）
   - 第二优先：返程车辆（`last_arrived_node_id=当前节点`，即车辆目的地是当前节点）
   - 第三优先：其他节点空闲车辆
3. **距离评分**：暂不实现（阶段5或阶段6补充，需先扩展`vehicles`表添加`current_longitude`/`current_latitude`字段）

#### 车辆返回规则（PRD要求）
**规则**：每个车辆的任务列表末尾自动追加一个 `is_return=true` 的返回任务，使车辆返回起始节点。

**返回任务格式**：
```json
{
  "from_node_code": "L1001",  // 最后一个目的节点
  "to_node_code": "L1001",    // 返回起始节点（车辆归属节点）
  "package_codes": [],        // 返回任务无包裹
  "is_return": true
}
```

**计算逻辑**：
- 最后一个运输任务的 `to_node_code` 作为返回任务的 `from_node_code`
- 车辆归属节点（`vehicles.node_id`）作为返回任务的 `to_node_code`
- `total_distance` 和 `total_time` 包含返回路程

#### F005调度流程（两次串行调用）

**调用阶段自动检测**：
- 检查是否存在该 `schedule_code` 的 `l0_l1_done` 或 `completed` 状态的批次
- 若不存在 → 首次调用（执行 L0→L1 调度）
- 若存在 `l0_l1_done` 批次 → 第二次调用（执行 L1→L2 调度）

**首次调用（L0→L1）**：
1. 查询条件：`from_node.node_type='storage_center'` AND `to_node.node_type='sorting_center'` AND `to_node.sorting_center.level=1` AND `packages.status='packed'`
2. 按 `from_node_code` 分组包裹
3. 对每个分组：
   - 查询该节点的空闲车辆（`status='idle'`）
   - 按优先级筛选候选车辆：
     1. 本节点空闲车辆（`node_id=当前节点` AND `status='idle'`）
     2. 返程车辆（`last_arrived_node_id=当前节点`，即车辆目的地是当前节点）
   - **评分计算**（规则评分+启发式）：
     - 对每个候选车辆，计算评分：`score = w1 × 总距离 + w2 × 总时间 + w3 × 包裹数`
     - 总距离：从车辆当前节点到目的节点的Haversine距离
     - 总时间：距离 / 平均速度（暂定60km/h）
     - 包裹数：当前车辆已分配包裹数 + 待分配包裹数
     - 选择**评分最低**的车辆（评分越低越好）
   - 按车辆载重匹配（大包裹配大车）：优先选择载重足够的车辆（`capacity` >= 包裹总重量，按 `capacity` 升序）
   - 分配包裹到车辆（直到车辆载重上限）
   - **添加返回任务**：在任务列表末尾追加 `is_return=true` 的返回任务
   - 计算 `total_distance` 和 `total_time`（包含返回路程）
   - 标记包裹为已分配（`dispatch_id=当前node_dispatch.id`）
4. 写入 `dispatch_batches` 和 `node_dispatches`（level_phase=0）
5. 更新批次状态为 `l0_l1_done`
6. **状态更新**（与PRD §F001-1/§F001-2一致）：
   - 包裹状态：`packed` → `in_transit`（PRD包裹表序号3：F005分配包裹到车辆 → 已打包 → 运输中）
   - 货物状态：`packed` → `in_transit`（PRD货物表序号4：F005分配包裹到车辆 → 已打包 → 运输中）
   - 车辆状态：`idle` → `delivering`
   - 司机状态：`idle` → `busy`
   - 订单状态：`delivering`（不变）

**第二次调用（L1→L2）**：
1. 前置条件：
   - `demo_mode=true`：检查是否存在 `l0_l1_done` 状态的批次，**直接执行**第二次调度
   - `demo_mode=false`：**由阶段6自动触发**（不在阶段4手动调用）
     - 第一次送达（L0→L1）完成后，阶段6自动检测 `pending_pack` 货物
     - 阶段6自动执行F021重新打包
     - 阶段6自动执行第二次F005（L1→L2调度，异步执行）
     - 详见《阶段6-模拟送达-开发文档.md》§2.2
2. 查询条件：`from_node.node_type='sorting_center'` AND `from_node.sorting_center.level=1` AND `to_node.node_type='sorting_center'` AND `to_node.sorting_center.level=0` AND `packages.status='packed'`
3. 后续流程同首次调用（包括添加返回任务）
4. 写入 `node_dispatches`（level_phase=1）
5. 更新批次状态为 `completed`
6. **状态更新**（与PRD §F001-1/§F001-2一致）：
   - 包裹状态：`packed` → `in_transit`（PRD包裹表序号3：F005分配包裹到车辆 → 已打包 → 运输中）
   - 货物状态：`packed` → `in_transit`（PRD货物表序号7：F005分配包裹到车辆 → 已打包 → 运输中）
   - 车辆状态：`idle` → `delivering`
   - 司机状态：`idle` → `busy`
   - 订单状态：`delivering`（不变）
   - **注意**：L1→L2包裹到达L2后通过 F013-1 模拟送达 → 包裹 `in_transit → delivered`、货物 `in_transit → delivered`、订单 `delivering → completed`

**demo_mode=true 的特殊处理**：
- 一次调用完成两次调度（L0→L1 和 L1→L2）
- 跳过 L1 送达等待，允许连续执行两次 F005
- 适用于课堂演示场景

#### （已弃用）第二次调用（L1→L2）- F005 已改为单次调用
**注意**：F005 已改为单次调用，自动检测包裹层级。原第二次调用逻辑保留仅供参考。
**前置条件**（二选一）：
- `demo_mode=true`：检查L0→L1是否已完成（`dispatch_batches.status='l0_l1_done'`）
- `demo_mode=false`：检查所有L0→L1的包裹已送达（L0→L1包裹`status='delivered'`，货物`status='pending_pack'`后经L1重新打包生成新包裹`status='packed'`）

**执行流程**：
1. 查询条件：`from_node.node_type='sorting_center'` AND `from_node.sorting_center.level=1` AND `to_node.node_type='sorting_center'` AND `to_node.sorting_center.level=0` AND `packages.status='packed'`（L1重新打包后包裹状态为已打包）
2. 后续流程同第一次调用（包括添加返回任务）
3. 写入 `node_dispatches`（level_phase=1）
4. **状态更新**（与PRD §F001-1/§F001-2一致）：
   - 包裹状态：`packed` → `in_transit`（PRD包裹表序号3：F005分配包裹到车辆 → 已打包 → 运输中）
   - 货物状态：`packed` → `in_transit`（PRD货物表序号7：F005分配包裹到车辆 → 已打包 → 运输中）
   - 车辆状态：`idle` → `delivering`
   - 司机状态：`idle` → `busy`
   - 订单状态：`delivering`（不变）
   - **注意**：L1→L2包裹到达L2后通过 F013-1 模拟送达 → 包裹 `in_transit → delivered`、货物 `in_transit → delivered`、订单 `delivering → completed`

### 3.4 算法评分公式

```
score = w1 × 总距离 + w2 × 总时间 + w3 × 包裹数
```

```json

    "w1": 0.5,
    "w2": 0.3,

  }
```

### 6.3 demo_mode实现

**决策**：`demo_mode` 作为请求参数，控制调度执行方式

**实现方式**：

1. **自动检测调用阶段**：
   - 检查是否存在该 `schedule_code` 的 `l0_l1_done` 或 `completed` 状态的批次
   - 若不存在 → 首次调用（执行 L0→L1 调度）
   - 若存在 `l0_l1_done` 批次 → 第二次调用（执行 L1→L2 调度）

2. **demo_mode=true**（演示模式）：
   - 一次调用完成两次调度（L0→L1 和 L1→L2）
   - 跳过 L1 送达等待，允许连续执行两次 F005
   - 适用于课堂演示场景

3. **demo_mode=false**（生产模式）：
   - 首次调用仅执行 L0→L1 调度
   - 第二次调用需等待 L1 实际送达完成
   - L0→L1 包裹送达后，货物状态变为 `pending_pack`
   - L1 重新打包后生成新包裹（状态 `packed`）
   - 检查存在 `l0_l1_done` 状态的批次后，才执行 L1→L2 调度

**代码逻辑**：

```python
# 自动检测调用阶段
existing_batch = db.query(DispatchBatch).filter(
    DispatchBatch.global_schedule_id == schedule.id,
    DispatchBatch.status.in_(['l0_l1_done', 'completed'])
).first()

if existing_batch:
    # 第二次调用：执行 L1→L2 调度
    if demo_mode or check_l0_l1_delivered(db, schedule):
        result = run_l1_to_l2_dispatch(db, schedule, vehicles, drivers)
        batch.status = 'completed'
    else:
        raise HTTPException(status_code=400, detail="L0→L1未完成，不能执行L1→L2")
else:
    # 首次调用：执行 L0→L1 调度
    result = run_l0_to_l1_dispatch(db, schedule, vehicles, drivers)
    batch.status = 'l0_l1_done'

db.flush()  # 刷新状态到数据库
```
