# 测试代码原则

> 基于 P1-3 阶段状态机重构后的测试故障修复经验总结。  
> 核心教训：**状态机是系统的"宪法"——测试必须遵守状态转换规则，不得绕过。**

---

## 核心原则

### 原则 1：测试必须走完整的状态机链路

**问题**：测试直接设置对象 `.status` 属性绕过状态转换校验，导致 P1-3 引入 `transition_*_status()` 后测试失败。

**正确做法**：测试必须完整模拟业务流程的每个状态转换环节。

```
❌ 错误：
pkg.status = 'packed'              # 直接设状态，绕过 F021 状态机
goods.status = 'delivered'         # 直接设状态，绕过送达确认流程

✅ 正确：
# 模拟完整链路：F007 → F021 → F005 → F006
schedule_result = global_schedule(...)
packages = packaging(schedule_result, schedule.id, db)
update_goods_after_f021(db, schedule.id)       # goods: pending_pack → packed
update_orders_after_f007(db, order_codes)       # orders: pending → delivering
dispatch_result = run_node_dispatch(db, ...)    # goods: packed → in_transit
```

### 原则 2：测试不得绕过 transition_*_status() 直接设状态

**项目宪章规则 16**：所有服务层不直接写 `.status`，统一走 `transition_*_status()`。

测试代码同样需要遵守。如果测试中需要设置特殊状态，必须使用合法的状态转换函数（或使用 `force=True` 仅限特殊场景）。

```
❌ 错误：
vehicle.status = 'delivering'     # 绕过状态机

✅ 正确（如果需要强制设置）：
transition_vehicle_status(db, vehicle, 'delivering')  # 正常转换
transition_vehicle_status(db, vehicle, 'maintenance', force=True)  # 特殊场景
```

### 原则 3：测试必须显式调用每个阶段的"激活函数"

P1-3 状态机将"状态批量转换"从算法函数中解耦到独立函数中。测试必须显式调用这些函数：

| 调度阶段 | 必要调用 | 效果 |
|----------|----------|------|
| F007 全局调度 | `update_orders_after_f007(db, order_codes)` | order: pending → delivering |
| F021 打包 | `update_goods_after_f021(db, schedule_id)` | goods: pending_pack → packed |
| F005 节点调度 | `run_node_dispatch()` 内部调用 `transition_*_status()` | goods: packed → in_transit |
| 模拟送达 L0→L1 | `SimulationService.deliver_packages()` | package: in_transit → delivered; goods 状态不变 |
| confirm-arrival | `transition_goods_status(db, goods, 'pending_pack')` | goods: in_transit → pending_pack |
| F021 重新打包 | `transition_goods_status(db, goods, 'packed')` | goods: pending_pack → packed |
| 模拟送达 L1→L2 | `transition_goods_status(db, goods, 'in_transit')` 再 `'delivered'` | goods: packed → in_transit → delivered |

### 原则 4：测试 fixture 的状态必须与现实流程一致

测试 fixture 创建实体时的初始状态，必须与当前测试所处流程阶段一致。

```
❌ 错误（simulation_pipeline fixture）：
goods = Goods(status="pending_pack")  # 但包裹已 in_transit，不一致

✅ 正确：
goods = Goods(status="in_transit")    # P1-3: 与包裹状态一致（F005 已调度）
```

### 原则 5：使用 JSON 字段时必须注意序列化/反序列化

数据库字段如 `order_codes`、`goods_schedules` 存储为 JSON 字符串，测试中手工创建对象时需要 `json.dumps()`，但在传递给函数时必须用原始 Python 对象。

```
❌ 错误：
schedule.order_codes = json.dumps(["O001", "O002"])
update_orders_after_f007(db, schedule.order_codes)  # 传了 JSON 字符串！

✅ 正确：
schedule.order_codes = json.dumps(order_code_list)
update_orders_after_f007(db, order_code_list)        # 传 Python list
```

### 原则 6：测试状态机必须了解允许的转换路径

P1-3 状态机有严格的转换规则，测试前必须了解每个实体的合法状态转换：

**Order 状态**：`pending → delivering → completed | exception`（不能跳过 delivering）

**Goods 状态**：`pending_pack → packed → in_transit → pending_pack（L1重打包）→ packed → in_transit → delivered`

**注意**：`pending → completed` 是非法转换！必须先经过 `delivering`。

### 原则 7：单元测试应测试业务逻辑，集成测试应测完整链路

- **单元测试**：可以 mock 外部依赖，但内部状态转换必须真实。
- **集成测试**：必须端到端运行，覆盖完整的 F007 → F021 → F005 → F006 链路。

本项目 P1-3 修复中，`test_node_dispatch.py`（单元测试）和 `test_auto_redispatch.py`/`test_dispatch_pipeline.py`/`test_simulation_pipeline.py`（集成测试）都需要在 F021 之后显式调用 `update_goods_after_f021()`。

## 常见错误模式速查

| 错误模式 | 根本原因 | 修复方式 |
|----------|----------|----------|
| `ValueError: 非法goods状态转换: pending_pack → in_transit` | F021 后缺少 `update_goods_after_f021()` | 在 F005 前添加调用 |
| `ValueError: 非法订单状态转换: pending → completed` | F007 后缺少 `update_orders_after_f007()` | 在状态流转前添加调用 |
| P1-3: deliver 后 goods 状态仍是 `in_transit` | 错误预期 deliver 会改 goods 状态 | P1-3 改为 confirm-arrival 模型 |
| `schedule.order_codes` 传 JSON 字符串给函数 | JSON 序列化/反序列化混淆 | 用原始 Python list |
| fixture 状态与实际流程阶段不匹配 | fixture 未同步更新 | 按当前流程阶段设置状态 |

## 状态机变更时的测试检查清单

当状态机发生变更时，按以下清单逐项检查所有测试：

- [ ] 所有直接 `.status =` 赋值是否改用 `transition_*_status()`？
- [ ] 每个调度阶段后是否调用了对应的 `update_*_after_*()` 函数？
- [ ] deliver 后的 goods 状态预期是否正确？（P1-3: 保持 `in_transit`）
- [ ] confirm-arrival + repack 流程是否在测试中正确模拟？
- [ ] fixture 实体初始状态是否与流程阶段一致？
- [ ] JSON 字段传递时是否正确序列化/反序列化？
- [ ] 订单状态转换是否经过 `delivering` 中间态？
