# R2-00 — 第二轮执行治理与证据基线

## 来源证据与当前行为

- 第一轮已建立计划状态、历史归档和证据规则，原文见[第一轮执行治理](../post_plan/第一轮优化计划/00-execution-governance.md)。
- 参考路线图明确指出：当前不足主要是并发、恢复、生产拓扑、容量和可观测性证据缺失，而不是普通 CRUD 数量不足。
- 当前 README/后端 README 仍可能保留历史测试数字；第二轮不得把历史快照当作当前实测。

## 问题与目标

为第二轮建立可审计的任务、环境、实验和发布基线，先冻结基线再实施并发协议，防止“代码完成但无法证明”。

## 范围

- 第一轮归档与第二轮实时计划的边界；任务 ID、依赖、分支、提交和 owner。
- SQLite 基线、PostgreSQL/Redis 目标拓扑、数据规模、并发客户端和故障注入点登记。
- 实验结果目录、原始输出、报告模板、回滚和 blocked/needs_decision 规则。

## 非目标

- 不在本卡修改业务代码或提前宣称 PostgreSQL、Docker、压测通过。
- 不重写第一轮历史结论；历史数字保留日期和语境。

## 依赖与进入条件

- 已切换到 `main`；工作区开始时干净。
- 第一轮计划已归档至 `My_doc/post_plan/第一轮优化计划/`。
- 参考路线图已评审，第二轮 7 张计划卡的依赖关系已确定。

## 有序实施步骤

1. 记录分支、工作树、依赖版本、当前测试基线和已有未验证项。
2. 建立实验登记表：环境、数据库、Redis、worker、数据量、请求分布、预热、持续时间和产物路径。
3. 将每个任务拆成实现、测试、运行验证、文档同步四类完成条件。
4. 规定失败记录必须保留原始日志；外部资源不可用时标 `blocked`，契约不明确时标 `needs_decision`。
5. 每张卡完成后回写 README、问题记录和当前文档，并检查链接、依赖无环和状态不越级。

## 验收标准

- 7 张第二轮计划卡均有唯一 ID、owner、依赖、进入条件、验收和回滚章节。
- README 是第二轮唯一实时聚合入口，第一轮目录只作历史追溯。
- 实验报告模板能记录硬件、软件版本、数据规模、worker、原始结果和结论。
- 未执行的 Docker/PostgreSQL/Redis/压测步骤明确为 pending 或 blocked。
